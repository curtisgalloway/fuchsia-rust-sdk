## Answer

Pilot 1 binds on the lock's `core.x64` under TCG on the first registration, with no
change to the driver source and none to the build. `scripts/emu driver
//drivers/simple_rust:pkg` publishes the package to the harness's `devhost` repository
and registers it; the driver index matches it to the edu device's composite node spec
`00_06_0`, the driver manager builds composite node `PCI0.bus.00_06_0.00_06_0` from
parents `pci` (`PCI0.bus.00_06_0`) and `acpi` (`acpi._SB_.PCI0.S30_.pt`), and the
driver starts in its own driver host, logs its three `Start` lines and adds its child
node `simple_child`. The harness's reboot path (a second `scripts/emu driver` with the URL
already registered) reboots the target and binds again.

## The backlog items for M11

### 1. Two copies of `libdriver_runtime.so`? No: one, the driver host's

`scripts/emu ffx driver host list`: the pilot runs alone in its own driver host
(`Driver Host: 43798 fuchsia-pkg://devhost/simple_rust_driver#meta/simple_rust_driver.cm`;
upstream's `.cml` has no `colocate`). `scripts/emu ffx target ssh "vmaps 43798"`: the
file-backed mappings are `simple_rust_driver.so` (the package's) and eight bootfs blobs,
identified by extracting the bundle's `system_a/fuchsia.zbi` with the IDK's `zbi
--extract` and reading each blob's `SONAME`:

| Mapped VMO | File |
|---|---|
| `bootfs:blob/50021291…` | `driver_host` (the executable; no soname) |
| `bootfs:blob/dca14ac9…` | `libc.so` (also the dynamic linker) |
| `bootfs:blob/459cee0a…` | `libdriver_runtime.so` (the blob M10 compared) |
| `bootfs:blob/a2cdd353…` | `libasync-default.so` |
| `bootfs:blob/11e9c510…` | `libfdio.so` |
| `bootfs:blob/dc8d6245…` | `libtrace-engine.so` |
| `bootfs:blob/29b85d28…` | `libstd-856d8f522a0d5cbd.so` |
| `bootfs:blob/c637d958…` | `libvfs_rust.so` |
| `vdso/stable` | `libzircon.so` |
| `simple_rust_driver.so` | the pilot (package blob `58f7dcca…`) |

None of the package's `lib/` blobs is mapped (`lib/libdriver_runtime.so` `59bb96ec…`,
`lib/libasync-default.so` `a6ba6382…`, `lib/libfdio.so` `3aa66cd3…`, `lib/libsvc.so`,
`lib/libtrace-engine.so`, `lib/ld.so.1`). The reason: `driver_host` is itself linked
against the runtime (`readelf -d` on its blob: `DT_NEEDED` libfdio, libvfs_rust,
libstd-856d8f522a0d5cbd, libzircon, libc, libasync-default, libdriver_runtime,
libtrace-engine), so every library in the pilot's `DT_NEEDED` (libasync-default, libc,
libdriver_runtime, libfdio, libzircon) is loaded before the driver is opened, and the
dynamic linker resolves the driver's needs to those modules by soname without asking the
package's loader.

Behaviour agrees: `scripts/emu ffx driver host show -r 43798` lists the pilot's two
dispatchers (`simple_rust_driver.cm-default`, `fuchsia-async`) in the host's runtime,
each `State: running` with processed requests; a driver on a second runtime copy would
register its dispatchers with that copy, invisible to the host's. The pure-Rust
`virtio-gpu-display` host (koid 10685) maps `459cee0a…` once, which is only *consistent
with* the same behaviour, not evidence for it: that driver's bootfs package ships its
`lib/libdriver_runtime.so` as the same blob `459cee0a…` as the host's, so its mapping
cannot tell the host copy from the packaged copy (review finding 1). The pilot's case is
the distinguishing one: its packaged copy is a different blob (`59bb96ec…`) and is not
mapped.

**Does it matter?** Not for loading: the packaged runtime libraries are fetched with the
package (about 1 MB) but not loaded; they would only be used for a library the host has
not already loaded. This is how the three pure-Rust `core.x64` drivers ship (M10) and
what `fuchsia_cc_driver` does, so the package stays as M10 made it. The one real
duplication is Rust's `std`: the pilot links `std` statically while `driver_host` loads
`libstd-<hash>.so`, so the process holds two `std` copies with separate statics (e.g.
panic hook, thread-local keys). Checked: both copies allocate through the one `libc.so`
in the process (Rust's `System` allocator on Fuchsia calls libc `malloc`; `vmaps` shows
only `scudo:` heap mappings), so memory can be freed across the boundary; and no `std`
type crosses the driver/host boundary in pilot 1 (the interface is the C ABI of
`__fuchsia_driver_registration__` and the driver runtime). The remedy would be to link
the release's `libstd-<hash>.so` dynamically, as GN does; its obstacle is that this
needs a toolchain build that matches that library exactly (same compiler build, `std`
build flags and crate hash); whether the lock's `rust_target` toolchain does is
unverified. Revisit if a
driver shows panic-hook or thread-local surprises, or passes `std` types across an FFI
boundary with the host (backlog).

## Findings for later milestones

- **G1:** the replay above is the whole sequence; budget about 1 minute to boot and
  15 s to register under TCG, 2 minutes if `scripts/emu driver` takes the reboot path.
  The acceptance lines to grep: `Driver    : fuchsia-pkg://devhost/simple_rust_driver#meta/simple_rust_driver.cm`
  and `Node      : PCI0.bus.00_06_0.00_06_0` in `composite show 00_06_0`, and
  `SimpleRustDriver::start() was invoked.` in `scripts/emu log simple_rust_driver`.
- **G1 / harness:** `ffx target wait`'s ssh retry message and empty backtrace may appear
  (intermittent) on stderr during the reboot path; harmless, but a replay script that treats stderr as
  failure would trip on it.
- **M12 / later Rust drivers:** the driver host preloads `libdriver_runtime.so`,
  `libasync-default.so`, `libfdio.so`, `libc.so`, `libtrace-engine.so`,
  `libstd-<hash>.so` and `libvfs_rust.so`; packaged copies of those are never loaded
  (only `libsvc.so` and anything else outside that set would be). A driver that links
  `std` or `vfs` statically holds its own copy beside the host's dylib.
- **Monitoring:** pure-Rust drivers need no `device_categories` to load; `static-checks`
  would fail any CI gate that runs it on upstream's manifest.

## Limitations

- Only x64 on the emulator; the arm64 package is built and tested but not loaded (M13's
  VIM3 is the first arm64 target).
- No device I/O (out of scope); the driver does not use its `pci` or `acpi` services.
- The "one runtime copy" answer rests on the host's memory map and runtime dump at this
  release; a future `driver_host` that stops linking the runtime itself would change it
  (the packaged copies would then be used).

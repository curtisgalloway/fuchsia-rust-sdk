So the exit is split: a pinned URL plus hash for `fidlgen_rust_next`, and "not
published" for `fidlgen_rust` (build from source in M7). The orchestrator decided
after review that M7 uses the `fidlgen_rust_next` pin ("Implications for M7").

**What "provably matches the release" means here.** The build ID cannot be recomputed
from the published file: lld's SHA-1 tree hash over the file with the note zeroed does
not match, and the file carries a `.gnu_debuglink` added after linking. The proof is
therefore a chain of anonymous reads: the release's `product_bundles.json` → build ids
(I1) → each build's `source_manifest.json` (revision `b5274053`) and `build-ids.json`
(label → `ad8c417e…`) → object `buildid/ad8c417e…/executable`, whose bytes contain that
ID, then pinned by SHA-256. It trusts the bucket's integrity the same way the lock's
other GCS pins do. The object was created 2026-09-17, before the release: the store is
keyed by build ID, and the release's builds produced an identical binary. The previous
release, `33.20260919.6.1`, also names `ad8c417e…`.

Corroboration (added after review): the binary's `.comment` section
(`readelf -p .comment`) names `rustc version 1.100.0-nightly (c26ce708d 2026-09-14)`,
`Fuchsia clang version 24.0.0git (… 3493720eca95cf844a8d7e58fdd12e0e5644e7d0)` and
`Fuchsia LLD 24.0.0 (… 3493720e…)`. These match the lock's `rust_host` pin
(`git_revisions:c26ce708…,3493720e…`) and `clang` pin (`git_revision:3493720e…`), the
toolchains `manifests/toolchain` names at `b5274053`.

  created 2026-09-17T01:00:53Z. Not downloaded.

**Encoding.** The object is stored gzip-encoded. A GET without `Accept-Encoding: gzip`
is decompressed by GCS (`warning: 214 UploadServer gunzipped`) and yields the ELF
(`c03f7086…`); with `Accept-Encoding: gzip` the body is the gzip stream (SHA-256
`5dbe799464a72ed64e2c164846bc265ad4c41db865b209238256e2a60acf9491`, MD5 equal to
`x-goog-hash`). Bazel 8.5.1 gets the ELF: a scratch module with
`http_file(urls = ["…/buildid/ad8c417e…/executable"], sha256 = "c03f7086…", executable = True)`
and the repository cache off fetched and verified it, and the fetched file ran
`--help`. (`bazel run @…//file` fails with "Not executable" because `//file` is a
filegroup; M7 needs a wrapper.)

**Retention.** The bucket's lifecycle is not readable anonymously
(`GET …/b/fuchsia-public-artifacts-release?fields=lifecycle` → 401). Older releases'
copies still exist (core.x64's `build-ids.json` → `buildid/<id>/executable` metadata):

## Building from source (for M7)

From a blobless fetch of `fuchsia.git` at `b5274053` (`git fetch --filter=blob:none
--shallow-since=2026-09-01 https://fuchsia.googlesource.com/fuchsia b5274053…`, 14 MB),
reading single files with `git cat-file -p b5274053:<path>`; no `git grep`.

**`fidlgen_rust` (Go).**
- `tools/fidl/fidlgen_rust/BUILD.bazel`: `go_binary_host_tool(name = "fidlgen_rust",
  srcs = ["main.go"], deps = ["//tools/fidl/fidlgen_rust/codegen", "//tools/fidl/lib/fidlgen"])`,
  loaded from `//build/bazel/rules/host:defs.bzl`, a wrapper over rules_go's
  `go_binary` (`@io_bazel_rules_go//go:def.bzl`) that adds host constraints.
- `codegen/BUILD.bazel`: `go_library` of `codegen.go`, `ir.go` with 11 `.tmpl` files as
  `embedsrcs`, importpath `go.fuchsia.dev/fuchsia/tools/fidl/fidlgen_rust/codegen`.
- `tools/fidl/lib/fidlgen/BUILD.bazel`: `go_library` of 10 files, **no deps** (standard
  library only); go-cmp is used by the tests only.
- `BUILD.gn` builds it through `bazel_host_tool` (`bazel_target = ":fidlgen_rust"`): upstream
  already builds it with Bazel. This probably explains its absence from `binaries.json`
  and the debug store (not verified).
- So M7 needs rules_go, a Go SDK, and three vendored directories with their

## Implications for M7

**Route decided by the orchestrator (2026-09-28, after review).** Design §4.2 builds
generators from source "unless I2 finds published prebuilts". So M7 fetches
`fidlgen_rust_next` by pin: `resolve_pins.py` resolves it per release from the lock's
core.x64 `build-ids.json`, requires every `host_x64` build to agree, checks the ELF
build-ID note and fails closed. Building it from source is the documented fallback.
`fidlgen_rust` is built from source with upstream's `BUILD.bazel`. Caveats accepted
with it: a debug-symbol store, not a distribution channel; retention unknown; host
glibc ≥ 2.18; unstripped binary.

The analysis that led to it:

- `fidlgen_rust` must be built from source. It is the smaller half: Go, standard
  library only, with upstream `BUILD.bazel` files. It needs rules_go and a pinned Go
  SDK (new module deps, C1: BCR plus a checksummed Go SDK download).
- `fidlgen_rust_next` can be fetched by the pin above. That removes the askama host
  crate tree (the design §8.2 risk) and `fuchsia-sync`'s host build from M7. Caveats for
  the orchestrator:
  1. The source is a debug-symbol store (`buildid/<id>/executable`), not a published
     host tool. Upstream could stop uploading it, and its lifecycle is unknown, though
     copies from 17 months ago still exist.
  2. It is the unstripped binary (5.8 MB), dynamically linked against the host glibc
     (≥ 2.18).
  3. Per release, `resolve_pins.py` would read one product build's `build-ids.json`
     (the lock's core.x64 build), take the ID labelled
     `//tools/fidl/fidlgen_rust_next:fidlgen_rust_next.actual(//build/toolchain:host_x64)`,
     require every `host_x64` build to agree (as I1 requires for revisions), check that
     the downloaded file's `.note.gnu.build-id` equals it, and record the decoded
     SHA-256. It must fail closed when the label or object is missing.
  4. The fallback is building from source (the plan's M7a).
- The plan's session split (M7a `fidlgen_rust_next`, M7b `fidlgen_rust`) still fits
  either way. If the pin is accepted, M7a shrinks to a lock entry, a repository rule and
  a wrapper target, and M7 could fit in one session.

## Limitations and blockers

- The build ID cannot be recomputed from the published file, so the release tie rests
  on the release's own manifests plus the ID note in the bytes (see "Answer").
- The debug store's retention policy is not readable anonymously.
- Not checked: whether the fetched `fidlgen_rust_next` generates correct bindings (M7's
  acceptance criterion), or the `host_x64-novariant` copy's contents.
- Neither generator is in a CIPD package or the IDK, so no CIPD tag route exists.

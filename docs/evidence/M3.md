## Milestone definition (moved from the plan)

**Design coverage:** R2 (runs on emulator), C6, design §7 "Emulator" row, W7 of the brief.
**Dependencies:** M2a.
**In scope:**
- `scripts/emu` (proposed name). It fetches QEMU and the `core.x64` product bundle for
  the lock's `sdk_version`, starts the emulator, and publishes a package. It also runs
  a component and registers a driver.
- The 6 container workarounds from `fuchsia-cloud-dev`'s README.
- **Portable across environments (owner direction 2026-09-27):** a plain setup script,
  with a Claude SessionStart hook only as a thin optional wrapper; KVM when
  `/dev/kvm` is usable, TCG otherwise; state and cache directories configurable, not
  tied to `~/`; root/IPv6 workarounds detected, not assumed; host requirements
  (network hosts, disk, optional KVM) documented as the contract.

**Out of scope:** driver binding (I3, M11); the VIM3.

### Implementation steps
1. Read `fuchsia-cloud-dev/dev` and decide: port the needed functions into this repo,
   keeping its BSD notice on ported code (C4), or call it as a pinned external tool.
   Record the decision in the M3 chapter. Porting is the default, so one repo carries
   one lock.
2. The product-bundle and QEMU versions derive from `overlay.lock.json`, not a second
   pin.
3. Package `hello_rust` as a component with `rules_fuchsia`. Its `.cml` uses
   `LogSink` from `parent/diagnostics` (per `fuchsia-cloud-dev`).
4. `scripts/emu start`, then `scripts/emu run //examples/hello_rust:pkg`.

### Acceptance criteria
- [x] The emulator boots the product bundle whose version equals the lock's
  `sdk_version`; show the `ffx target show` version.
- [x] `hello_rust` runs and its line appears in `ffx log`.
- [x] A second `scripts/emu start` with the bundle cached takes under 2 minutes.
- [x] Setup failure (a blocked host) exits non-zero naming the host.
- [x] Total disk use after setup, build and boot is within the active profile's budget
  (hosted: ≤ 25 GB), shown by the M2a disk report.
- [x] With KVM unavailable (the hosted profile) the harness uses TCG without flags;
  the KVM path is exercised at least by a unit test of the detection logic.

### Testing and review
- Verify with the commands above, recording boot time and total disk after setup.
- Review focus: no second version pin, workarounds commented with their reason, and
  license of ported code.
- Review method: inherit (a reviewer subagent with fresh context).

- **hello_rust:** "its `.cml` uses `LogSink` from `parent/diagnostics` … Always run ffx
  with a short isolate dir (QEMU unix-socket path limit)."

4 vCPU; no `ssh`/`ssh-keygen`; no IPv6 (`/proc/net/if_inet6` absent); Ubuntu 24.04,

### Where each per-release input comes from (no second pin)

| Input | Source | Pinned by |
|---|---|---|
| ffx | `@fuchsia_idk//tools/x64/ffx` | the lock's `bazel_sdk` SHA-256 (the IDK tarball) |
| QEMU | `@fuchsia_idk//tools/x64/qemu_internal` (QEMU 11.0.2) | the same SHA-256. Its `.versions/qemu.cipd_version` names `fuchsia/third_party/qemu/linux-amd64` instance `TDWhWdNilJMXsvMLvdrLeqjo8KHaGUEQUB82NHMFPXEC`, which is exactly what fuchsia.git's `manifests/jiri.lock` records at the lock's `fuchsia_revision` (`manifests/prebuilts`: `git_revision:e545d8bb9d63e9dd61542b88463183314cff9482`; read by a depth-1 blobless git fetch). No `qemu` lock field was needed |
| `core.x64` bundle | the lock's own `sdk_version.source`, `…/33.20260927.4.1/product_bundles.json` → the `core.x64` entry's `transfer_manifest_url` (`gs://fuchsia-public-artifacts-release/builds/8669503301662913825/product_bundles/core.x64/transfer.json`) → `ffx product download --auth no-auth` | **not pinned by hash** (below) |

**Tamper evidence of the product bundle, honestly:** nothing upstream pins the bundle's
files by content hash that the lock could record. `transfer.json` names 661 blobs (each
name is the blob's merkle root, so package blobs are content-addressed and the target's
package resolver checks them against the bundle's TUF metadata) and 174 files by path
only; `product_bundle.json` has no image hashes. The boot images (`fuchsia.zbi`,
`fuchsia.vbmeta`, `fxfs.sparse.blk`) are therefore trusted by URL over HTTPS from the
release's GCS path. What the harness adds: it refuses a bundle whose
`product_bundle.json` does not say `product_name: core.x64`, `product_version` and
`sdk_version` equal to the lock's, and it writes the SHA-256 of every downloaded file to
`pb/core.x64-<V>.sha256.json` (a record for later comparison, not a pin). Backlog item
and owner question below.

### The six `fuchsia-cloud-dev` workarounds

| # | Workaround | In this repo |
|---|---|---|
| 1 | No `ssh` client | detected (`ssh_plan`): present → nothing; missing, root and `apt-get` → `apt-get install openssh-client` (retry after `apt-get update`); otherwise stop with what to install. Exercised live (installed here) |
| 2 | QEMU socket paths < 108 bytes | isolate dir `<emulator>/ffx`, configurable; `check_socket_room` fails early naming `OVERLAY_FFX_ISOLATE_DIR`. Measured: ffx puts `qmp`, `serial`, `monitor` in `<isolate>/data/emu/instances/<name>/`; 87 bytes with the default |
| 3 | No IPv6 | detected (`ipv6_loopback` binds `::1`): without it the package server binds `127.0.0.1:8083`, with it ffx's default |
| 4 | Running as root | `rules_python`'s `ignore_root_user_error` in `MODULE.bazel` (since M2); it has no effect for other users, so it needs no detection |
| 5 | Execroot-relative package manifests | `ffx repository publish` runs from `bazel info execution_root` |
| 6 | Driver URL sticks until reboot | `scripts/emu driver` reboots before re-registering a listed URL. **Untested** (no driver before M10; M11 exercises it) |

Each is commented at its site in `emu.py` / `emu_env.py`.

## Deviations from the plan text

- **QEMU comes from the IDK, not from a separate fetch** (the plan said the harness
  "fetches QEMU"): the release's IDK already ships the release's QEMU pin, so no new
  lock field was added (the task allowed one if needed).
- **Python, not bash.** `scripts/emu` is a two-line entry into `scripts/emu.py`, so the
  detection logic has unit tests; the scripts already need python3 ≥ 3.11.
- **No SessionStart hook** in M3 (optional per the owner); README shows the thin wrapper.
- **`scripts/emu driver` is ported but not exercised** (no driver package exists
  before M10).
- **`scripts/emu check` and `scripts/emu env`** are additions: the version criterion and
  the host contract made checkable.
- ffx analytics are disabled in the harness's isolate directory (`setup`).

## Limitations and open items

- **Owner question — pin the product bundle by hash?** Recommendation: add a lock field
  through `resolve_pins.py` holding a digest over the bundle's file SHA-256s (the record
  `scripts/emu` already writes), checked after download. Cost: `resolve_pins.py`
  downloads 364 MB more per run. Until then the bundle is trusted by URL and HTTPS.
- `ffx repository server list` keeps listing a stopped server (stale entry; nothing
  listens on 8083 afterwards).
- The emulator disk image can grow toward 10 GiB with guest writes.
- Setup's preflight checks reachability, not every URL a download uses; a host that
  fails mid-download surfaces as the ffx or Bazel error.

## How to start it again

The emulator was left stopped. `scripts/emu setup` (seconds when cached), then
`scripts/emu start` (about 1 minute), `scripts/emu check`, `scripts/emu run
//examples/hello_rust:pkg`, `scripts/emu log hello_rust`; `scripts/emu stop` when done.

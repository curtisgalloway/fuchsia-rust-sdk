## Milestone definition (moved from the plan)

**Design coverage:** R2 (runs on emulator), C6, design §7 "Emulator" row, W7 of the brief.
**Dependencies:** M2a.
**In scope:**
- `scripts/emu` (proposed name). It fetches QEMU and the `core.x64` product bundle for
  the lock's `sdk_version`, starts the emulator, and publishes a package. It also runs
  a component and registers a driver.
- The 6 container workarounds from `fuchsia-cloud-dev`'s README.
- **Portable across environments (owner direction 2026-09-27):** a plain setup script,
  with a Claude SessionStart hook only as a thin optional wrapper; KVM when
  `/dev/kvm` is usable, TCG otherwise; state and cache directories configurable, not
  tied to `~/`; root/IPv6 workarounds detected, not assumed; host requirements
  (network hosts, disk, optional KVM) documented as the contract.

**Out of scope:** driver binding (I3, M11); the VIM3.

### Implementation steps
1. Read `fuchsia-cloud-dev/dev` and decide: port the needed functions into this repo,
   keeping its BSD notice on ported code (C4), or call it as a pinned external tool.
   Record the decision in the M3 chapter. Porting is the default, so one repo carries
   one lock.
2. The product-bundle and QEMU versions derive from `overlay.lock.json`, not a second
   pin.
3. Package `hello_rust` as a component with `rules_fuchsia`. Its `.cml` uses
   `LogSink` from `parent/diagnostics` (per `fuchsia-cloud-dev`).
4. `scripts/emu start`, then `scripts/emu run //examples/hello_rust:pkg`.

### Acceptance criteria

- [x] `hello_rust` runs and its line appears in `ffx log`.

### Where each per-release input comes from (no second pin)

| Input | Source | Pinned by |
|---|---|---|
| ffx | `@fuchsia_idk//tools/x64/ffx` | the lock's `bazel_sdk` SHA-256 (the IDK tarball) |
| QEMU | `@fuchsia_idk//tools/x64/qemu_internal` (QEMU 11.0.2) | the same SHA-256. Its `.versions/qemu.cipd_version` names `fuchsia/third_party/qemu/linux-amd64` instance `TDWhWdNilJMXsvMLvdrLeqjo8KHaGUEQUB82NHMFPXEC`, which is exactly what fuchsia.git's `manifests/jiri.lock` records at the lock's `fuchsia_revision` (`manifests/prebuilts`: `git_revision:e545d8bb9d63e9dd61542b88463183314cff9482`; read by a depth-1 blobless git fetch). No `qemu` lock field was needed |
| `core.x64` bundle | the lock's `product_bundle.url` (`gs://fuchsia-public-artifacts-release/builds/8669503301662913825/product_bundles/core.x64/transfer.json`, taken by `resolve_pins.py` from the release's `product_bundles.json`) → `ffx product download --auth no-auth` | the lock's `product_bundle.value`: a digest over every file (below) |

**The product bundle pin (owner decision "yes, pin the bundle by hash").** Upstream
pins none of the bundle's files by content: `transfer.json` names 661 blobs (each name
is the blob's merkle root, which the target's package resolver checks against the
bundle's TUF metadata) and 174 files by path only, and `product_bundle.json` has no
image hashes. So `resolve_pins.py` now writes:

```json
"product_bundle": {
  "files": 835,
  "product": "core.x64",
  "source": [
    "https://storage.googleapis.com/fuchsia/development/33.20260927.4.1/product_bundles.json",
    "https://storage.googleapis.com/fuchsia-public-artifacts-release/builds/8669503301662913825/product_bundles/core.x64/transfer.json"
  ],
  "url": "gs://fuchsia-public-artifacts-release/builds/8669503301662913825/product_bundles/core.x64/transfer.json",
  "value": "4b341c52f73f202b65a5d6619858c49f9e2056866e4902735efbf7a78ae32aab"
}
```

**Definition of `value`** (`resolve_pins.bundle_digest`, used by both the resolver and
the harness; also in the `resolve_pins.py` docstring): SHA-256 over the UTF-8 lines
`<path>\t<sha256>\n`, one per file, sorted by path. `<path>` is the file's path inside
the downloaded bundle directory: for each `transfer.json` entry, its `local` minus the
leading `product_bundle`, then the file name (`blobs/1/<merkle>`, `product_bundle.json`,
`system_a/fuchsia.zbi`, …). `<sha256>` is the hex SHA-256 of the file's bytes as GCS
serves them from `https://storage.googleapis.com/<bucket>/<remote>/<name>` (checked live
to equal what `ffx product download` writes). The resolver streams every file (8 at a
time, never stored: ~364 MB more per resolve, disk peak 0.01 GiB), rejects unsafe paths,
duplicates, unknown entry types and a manifest version other than `"1"`, and names the
field on any failure. The harness hashes the downloaded bundle (`.partial`) and refuses
and deletes it on a mismatch (count or digest); `setup` re-verifies a cached bundle
(about 1 s), `scripts/emu verify` does so on demand, and `start` requires a setup
recorded for the lock's digest. It still also checks that `product_bundle.json` says
`core.x64` and the lock's version.

**The image is `core`** (established by the reviewer, resolving my "minimal" surprise):
the release lists one `core.x64` bundle (661 blobs, 174 files, versus `minimal.x64`'s
522/150), and `fuchsia-cloud-dev`'s older `core.x64` also carries the build-info
product name `minimal`. On the booted target, `core/testing` has `devices-tests`,
`ffx-laboratory` exists, `enable_ephemeral_drivers` is `true`, and the `edu` device shows
as `PCI0.bus.00_06_0` (VID 0x1234, DID 0x11e8, unbound, a composite node spec), which is
what I3 and M11 need.

### The six `fuchsia-cloud-dev` workarounds

| # | Workaround | In this repo |
|---|---|---|
| 1 | No `ssh` client | detected (`ssh_plan`): present → nothing; missing, root and `apt-get` → `apt-get install openssh-client` from the host's configured mirrors (retry after `apt-get update`; if that fails, apt's own error is reported with what to do); otherwise stop with what to install. The apt mirrors are not in the preflight (review finding 3). Exercised live (installed here) |
| 2 | QEMU socket paths < 108 bytes | isolate dir `<emulator>/ffx`, configurable; `check_socket_room` fails early naming `OVERLAY_FFX_ISOLATE_DIR`. Measured: ffx puts `qmp`, `serial`, `monitor` in `<isolate>/data/emu/instances/<name>/`; 87 bytes with the default |
| 3 | No IPv6 | detected (`ipv6_loopback` binds `::1`): without it the package server binds `127.0.0.1:8083`, with it ffx's default |
| 4 | Running as root | `rules_python`'s `ignore_root_user_error` in `MODULE.bazel` (since M2); it has no effect for other users, so it needs no detection |
| 5 | Execroot-relative package manifests | `ffx repository publish` runs from `bazel info execution_root` |
| 6 | Driver URL sticks until reboot | `scripts/emu driver` reboots before re-registering a listed URL. **Untested** (no driver before M10; M11 exercises it). `dev`'s `sleep 5` and log dump after `driver register` were not ported: use `scripts/emu log <name>` |

Each is commented at its site in `emu.py` / `emu_env.py`.

## Deviations from the plan text

- **QEMU comes from the IDK, not from a separate fetch** (the plan said the harness
  "fetches QEMU"): the release's IDK already ships the release's QEMU pin, so no `qemu`
  lock field was added (the task allowed one if needed).
- **A new lock field, `product_bundle`** (owner decision "yes, pin the bundle by hash"),
  so `resolve_pins.py` streams ~364 MB more per run.
- **Python, not bash.** `scripts/emu` is a two-line entry into `scripts/emu.py`, so the
  detection logic has unit tests; the scripts already need python3 ≥ 3.11.
- **No SessionStart hook** in M3 (optional per the owner); README shows the thin wrapper.
- **`dev test` not ported** (review finding 2, decided by the orchestrator): listed in
  `emu.py`'s "Changes from dev"; the plan's M16 scope now includes `scripts/emu test`.
- **`scripts/emu driver` is ported but not exercised** (no driver package exists
  before M10), and `dev`'s `sleep 5` + log dump after registering is dropped (review
  finding 5, recorded).
- **`scripts/emu verify`, `check` and `env`** are additions.
- ffx analytics are disabled in the harness's isolate directory (`setup`).
- Fuchsia's `PATENTS` added at `third_party/fuchsia/PATENTS` (orchestrator's nit).

## Limitations and open items

- `ffx repository server list` keeps listing a stopped server (stale entry; nothing
  listens on 8083 afterwards).
- The emulator disk image can grow toward 10 GiB with guest writes (backlog).
- Setup's preflight checks reachability, not every URL a download uses; a host that
  fails mid-download surfaces as the ffx or Bazel error. apt's mirrors are not probed.
- The bundle digest pins file contents, but the lock trusts `product_bundles.json` and
  `transfer.json` at resolve time (HTTPS from the release's GCS paths), as it already
  trusts the IDK's URL.

## How to start it again

The emulator was left stopped. `scripts/emu setup` (seconds when cached), then
`scripts/emu start` (about 1 minute), `scripts/emu check`, `scripts/emu run
//examples/hello_rust:pkg`, `scripts/emu log hello_rust`; `scripts/emu stop` when done.

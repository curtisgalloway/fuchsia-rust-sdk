## Milestone definition (moved from the plan)

**Design coverage:** R5 (tools), A4, D7. **Dependencies:** I2, M6b.
**In scope:** `tools/fidlgen_rust_next`, fetched by pin (added to the lock), and
`tools/fidlgen_rust`, built from source at the revision with `rules_go` and upstream's
`BUILD.bazel` (route below).

**Out of scope:** the binding rule (M8).

**Route (orchestrator decision, 2026-09-28, after I2's review):** `fidlgen_rust_next`
is **fetched by pin** from the release's public debug-symbol store
(`buildid/<id>/executable`; URL, hash and resolution in [I2 evidence](I2.md),
"Implications for M7"); building it from source is the documented fallback.
`fidlgen_rust` is **built from source** (not published): Go, standard library only,
upstream `BUILD.bazel` files (`go_binary_host_tool` wraps rules_go's `go_binary`), no Go
module downloads. Caveats: a debug-symbol store, not a distribution channel; retention
unknown; host glibc ≥ 2.18; unstripped binary.

### Implementation steps
1. `fidlgen_rust_next` (prebuilt): `resolve_pins.py` resolves the build ID from the
   lock's core.x64 `build-ids.json` (label
   `//tools/fidl/fidlgen_rust_next:fidlgen_rust_next.actual(//build/toolchain:host_x64)`),
   requires every `host_x64` build of the release to agree, downloads
   `buildid/<id>/executable`, checks its `.note.gnu.build-id`, records the SHA-256 of the
   decoded bytes in the lock, and fails closed on any mismatch or missing object. Add a
   repository rule (`http_file` exposes a filegroup, so wrap it in an executable target).
   Fallback, only if the pin route fails: build from source (Rust 2024, `BUILD.gn` only;
   deps `fidl_ir`, `fidlgen_rs`, `fuchsia-sync`, crates argh/askama/bitflags/serde/
   serde_json, 28 packages in the unfiltered Cargo.lock closure; a hand-written
   `overlays/tools/fidl/fidlgen_rust_next/BUILD.bazel`).
2. `fidlgen_rust` (source): vendor `tools/fidl/fidlgen_rust` and `tools/fidl/lib/fidlgen`
   via `regen.py vendor` with upstream's `BUILD.bazel` (loads rewritten:
   `go_binary_host_tool` → `go_binary`, test macros dropped). Add `rules_go` and a pinned
   Go SDK to `MODULE.bazel`.
3. Run both on the IR of one small IDK library (`fuchsia.mem`), produced by the IDK's
   `fidlc`.

### `fidlgen_rust_next` resolution (lock field)

`resolve_fidlgen_rust_next(up, version)`: reads `product_bundles.json`; requires exactly
one build named `core.x64`; reads every product build's
`builds/<id>/build-ids.json`; the label
`//tools/fidl/fidlgen_rust_next:fidlgen_rust_next.actual(//build/toolchain:host_x64)`
must map to one ID in core.x64, and every build naming the label must give the same
single ID (builds that do not name it are skipped: core.vim3 builds only
`host_x64-novariant`); fetches `buildid/<id>/executable` (urllib sends no
`Accept-Encoding`, so GCS serves the decoded ELF, as Bazel's download sees it); parses
the ELF64 section headers (little-endian, x86-64, SHT_NOTE, owner `GNU`, type 3) and
requires the set of build IDs to be exactly `{id}`; records
`{"build_id", "url", "value": SHA-256, "source": [product_bundles.json, the agreeing
build-ids.json files, the executable]}`. It is resolved after `product_bundle`, so the
existing failure tests keep their field names; any failure names `fidlgen_rust_next`
and leaves the lock unchanged.

Result for `33.20260927.4.1`: 7 of 8 builds name `ad8c417e211deb69e793b2d354c96c310416fc3c`
(core.vim3 names only `host_x64-novariant`, `fb62c8a7…`); value
`c03f7086aa6de3dbfa1cc06647d2667455d81c7f539f3d932ec08bd4fe5ee1ae`, the bytes I2 pinned.
`go`: `4f8a8a8e7315660fe818a2ef914ff333433a87f7345d147b8a8291d8095b0d61`

### C1: what the new pieces download

- Everything new was first fetched under the allowlist above: `rules_go`, `gazelle`
  (loaded because rules_go's `MODULE.bazel` uses its extension), `rules_shell`,
  `package_metadata`, `platforms` 1.1.0 from BCR/github.com; `@fuchsia_go` from CIPD;
  `@fidlgen_rust_next` from GCS. No Go module is fetched: `gazelle`'s `go_deps`
  extension only declares rules_go's own dev repositories (none fetched; no
  `com_github_*`/`org_golang_*` directory in the output base), and no `go_download_sdk`
  repository exists.
- **Surprise: go.dev metadata.** rules_go's `go_sdk` extension, for rules_go's own
  `go_default_sdk` (never selected; the root module's `wrap` is registered first), asks
  `https://go.dev/dl/?mode=json&include=all` for SDK hashes when the lockfile's `facts`
  lack them, with `allow_fail = True`, and stores the answer as `facts` in
  `MODULE.bazel.lock`. `@go_toolchains` also registers `go_default_sdk` (go1.25.0) as a
  fallback toolchain for exec platforms the wrapped SDK does not cover: on an exec
  platform other than linux-amd64 it would download go1.25.0 from go.dev/dl.google.com,
  checked against the SHA-256 in the facts. The overlay's build host is linux-amd64
  only (C5), so it is never selected (review finding 1). Checked in a scratch output base and repository cache with
  go.dev blocked: `bazel query 'deps(//vendor/fuchsia/tools/fidl/fidlgen_rust)'` with the
  committed facts and `--lockfile_mode=error` exits 0 (the extension ran; no request
  needed), and with `--lockfile_mode=off` (no facts) also exits 0 (the blocked request
  is tolerated). Decision: keep the facts (go1.25.0 file names and SHA-256s) in the
  lockfile, so builds with it never contact go.dev. Nothing is downloaded from go.dev
  in either case.

## Deviations from the plan text

- **Step 2's directory list grew:** besides `tools/fidl/fidlgen_rust` and
  `tools/fidl/lib/fidlgen`, `tools/fidl/fidlgen_rust/codegen` is listed separately
  (regen.py leaves out subdirectories with their own `BUILD.bazel`), and
  `tools/fidl/fidlgen_rust_next/configs` (overlay BUILD) plus fuchsia.git's root
  `rustfmt.toml` are vendored: both generators need them as upstream runs them, and
  M8 will too.
- **Two patches** under `patches/fuchsia/tools/fidl/fidlgen_rust/`: visibility for
  `//tools/fidlgen_rust`, and exporting the goldens (this Bazel does not export source
  files implicitly).
- **`toolchain/rust.BUILD.bazel`** exposes `bin/rustfmt` and `:rustc_lib` (marked
  "Overlay:").
- **`platforms` 1.0.0 → 1.1.0** (MVS would pick 1.1.0 anyway, and Bazel warned).
- **Golden tests** go beyond the plan's "diffs cleanly … where a reference is
  available": the only upstream references are the generators' goldens over fidlc's
  IR goldens, so the test data is 5 IR goldens and 10 `fidlgen_rust_next` goldens
  copied by hand (0.8 MB), not every fidlc golden through regen.py (112 files).
- For the orchestrator (design text, not changed here): A4 is resolved (the Go
  generator builds from source with only rules_go and the release's Go SDK; the Rust
  generator is taken prebuilt), and R1's lock gains `go` and `fidlgen_rust_next`.

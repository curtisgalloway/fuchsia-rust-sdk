## Investigation definition (moved from the plan)

**Design coverage:** I1 (blocks R1). **Dependencies:** none.
**Question:** which published, anonymously readable artifact maps `33.20260927.4.1` to
a `fuchsia.git` commit?
**Evidence to collect (in order; stop at the first that works for two releases):**
1. The IDK's `meta/manifest.json`, streamed without downloading 3 GB.
2. The GCS release directory (`gs://fuchsia/development/<version>/`) over the JSON API,
   looking for `jiri.snapshot`, `source_manifest.json` or similar.
3. The Bazel SDK CIPD package tags (`git_revision`, `version`).
4. Git tags or refs on `fuchsia.googlesource.com/fuchsia` named after the release.
5. The Buildbucket recipes in `fuchsia-ci`'s `fuchsia-release-artifacts-ci-handoff.md`
   (private repo).

**Exit:** a lookup that returns the revision for `33.20260927.4.1` and one earlier
release, documented here with the exact requests. If none works anonymously, stop and
report; R1 and everything after it are blocked.

**Method** (all anonymous HTTPS GETs/POSTs, no credentials, no gitiles):

1. `GET https://storage.googleapis.com/fuchsia/development/<V>/product_bundles.json`.
   Each entry has `product_version` (asserted equal to `<V>`) and a
   `transfer_manifest_url` of the form
   `gs://fuchsia-public-artifacts-release/builds/<buildbucket id>/product_bundles/<name>/transfer.json`.
2. For each build id:
   `GET https://storage.googleapis.com/fuchsia-public-artifacts-release/builds/<id>/source_manifest.json`.
   `directories["."].git_checkout` has `repo_url`
   `https://fuchsia.googlesource.com/fuchsia` and `revision`, the `fuchsia.git` commit;
   `directories["integration"].git_checkout.revision` is the integration commit.
   (`jiri_snapshot.xml` in the same directory carries the same `fuchsia` revision;
   checked for the core.x64 build of `33.20260927.4.1` only.)
3. Tie the IDK to those builds through CIPD:
   `POST https://chrome-infra-packages.appspot.com/prpc/cipd.Repository/ResolveVersion`
   with `{"package":"fuchsia/sdk/core/linux-amd64","version":"version:<V>"}`, then
   `POST …/DescribeInstance` with that instance and `"describeTags":true`. The instance
   carries `git_revision:<integration commit>`, `jiri_snapshot:<V>` and `version:<V>`.
4. Accept only if every product build reports the same `fuchsia.git` and integration
   revisions, and that integration revision equals the IDK's CIPD `git_revision`.
   Anything else fails (non-zero exit), never a guess.

Why this identifies the IDK's commit, not only the products': the IDK instance is tagged
with the same integration commit that pinned `fuchsia.git` for all the product builds,
and the IDK's content matches that commit (cross-check below).

### The lookup, as run (`lookup.sh`, scratch; M1 turns it into `resolve_pins.py`)

```bash
#!/usr/bin/env bash
# I1 lookup: SDK version -> fuchsia.git revision, anonymously.
# Usage: lookup.sh <sdk-version>
set -euo pipefail
V="$1"
GCS=https://storage.googleapis.com
CIPD=https://chrome-infra-packages.appspot.com/prpc/cipd.Repository

# 1. The release's product bundle index names the Buildbucket builds.
curl -sSf "$GCS/fuchsia/development/$V/product_bundles.json" > "pb-$V.json"

# 2. Each build directory publishes source_manifest.json.
echo "== product builds for $V: <build id> <name> <fuchsia.git> <integration>"
python3 - "$V" <<'EOF' > "builds-$V.txt"
import json, re, sys
for p in json.load(open(f"pb-{sys.argv[1]}.json")):
    assert p["product_version"] == sys.argv[1], p
    print(re.search(r"builds/(\d+)/", p["transfer_manifest_url"]).group(1), p["name"])
EOF
while read -r id name; do
  curl -sSf "$GCS/fuchsia-public-artifacts-release/builds/$id/source_manifest.json" \
    | python3 -c "
import json, sys
d = json.load(sys.stdin)['directories']
f, i = d['.']['git_checkout'], d['integration']['git_checkout']
assert f['repo_url'] == 'https://fuchsia.googlesource.com/fuchsia', f
print('$id', '$name', f['revision'], i['revision'])"
done < "builds-$V.txt" | tee "revs-$V.txt"

# 3. The IDK's CIPD instance for this version, and its git_revision tag
#    (the integration.git commit the SDK builder ran from).
H=$(curl -sSf -X POST -H 'Content-Type: application/json' -H 'Accept: application/json' \
      -d "{\"package\":\"fuchsia/sdk/core/linux-amd64\",\"version\":\"version:$V\"}" \
      "$CIPD/ResolveVersion" | tail -n +2 | python3 -c 'import json,sys; print(json.load(sys.stdin)["instance"]["hexDigest"])')
SDK_INTEGRATION=$(curl -sSf -X POST -H 'Content-Type: application/json' -H 'Accept: application/json' \
      -d "{\"package\":\"fuchsia/sdk/core/linux-amd64\",\"instance\":{\"hashAlgo\":\"SHA256\",\"hexDigest\":\"$H\"},\"describeTags\":true}" \
      "$CIPD/DescribeInstance" | tail -n +2 | python3 -c '
import json, sys
tags = {t["key"]: t["value"] for t in json.load(sys.stdin)["tags"]}
print(tags["git_revision"])')
echo "== IDK CIPD instance $H, git_revision (integration) $SDK_INTEGRATION"

# 4. Verdict: every product build agrees, and its integration commit is the IDK's.
python3 - "$V" "$SDK_INTEGRATION" <<'EOF'
import sys
rows = [l.split() for l in open(f"revs-{sys.argv[1]}.txt")]
fx = {r[2] for r in rows}; integ = {r[3] for r in rows}
assert len(fx) == 1 and len(integ) == 1, (fx, integ)
assert integ == {sys.argv[2]}, ("IDK integration differs", integ, sys.argv[2])
print(f"RESULT {sys.argv[1]} fuchsia.git={fx.pop()} integration={sys.argv[2]} builds={len(rows)}")
EOF
```

## Cross-check: IDK content matches the revision

Independent of step 3: each release's IDK was streamed once more and only `fidl/` kept
(`curl -sS …/sdk/linux-amd64/core.tar.gz | tar -xzf - --wildcards 'fidl/*'`, 7 MB kept,
about 90 s). Every IDK `.fidl` file's `git hash-object` id was looked up among the
`.fidl` blob ids of a commit's tree (trees only, from
`git fetch --filter=blob:none --shallow-since=2026-09-18 https://fuchsia.googlesource.com/fuchsia refs/heads/main`).

```bash
#!/usr/bin/env bash
# Corroboration: do the IDK's .fidl files exist, byte for byte, in fuchsia.git at <commit>?
# Compares git blob ids (no blob download needed; trees only).
# Usage: fidlcheck.sh <idk-extract-dir> <commit>...
set -euo pipefail
DIR="$1"; shift
find "$DIR/fidl" -name '*.fidl' -type f | sort > /tmp/idk-fidl-list.$$
xargs git hash-object < /tmp/idk-fidl-list.$$ > /tmp/idk-fidl-hash.$$
TOTAL=$(wc -l < /tmp/idk-fidl-list.$$)
for C in "$@"; do
  git -C fxt.git ls-tree -r "$C" | awk '$4 ~ /\.fidl$/ {print $3}' | sort -u > /tmp/tree-fidl.$$
  MISS=$(sort -u /tmp/idk-fidl-hash.$$ | comm -23 - /tmp/tree-fidl.$$ | wc -l)
  echo "$C: IDK .fidl files=$TOTAL, blob ids absent from commit's .fidl files=$MISS"
done
rm -f /tmp/idk-fidl-list.$$ /tmp/idk-fidl-hash.$$ /tmp/tree-fidl.$$
```

## Limitations and notes

- The mapping goes through **product builds** of the same version. If a release ever
  publishes an IDK without product bundles, step 1 404s and the lookup fails (closed).
- Failure path: unknown version `33.20260927.9.9` → `product_bundles.json` 404,
  `curl: (22)`, exit 22.
- Older releases: `32.20260505.0.1` and `28.20250501.7.1` resolve (9 builds agree).
  `20.20240404.1.1` does **not**: builds share integration `1a83680c…` but report 5
  different `fuchsia.git` revisions, so the agreement check rejects it. The method is
  shown for current releases only; M1 must keep the agreement check.
- **For M1 step 2.5 (not an I1 criterion):** `fuchsia/sdk/core/fuchsia-bazel-rules/linux-amd64`
  resolves neither `version:33.20260927.4.1` nor `git_revision:1463df67…` (404 "no such
  tag"; its `latest` was registered 2026-09-22), while `fuchsia/development/rules_fuchsia`
  does resolve `git_revision:1463df67…` (instance `8d346b9a…`). M1 must decide how to pin
  the Bazel SDK for releases without a tagged instance.

### How the walker differs from the brief's

The brief's App. B walker matches `deps = [ ... ]` with regular expressions inside the
target's block. At this revision that misses whole files: bazel2gn-generated BUILD.gn
files (for example `src/lib/diagnostics/log/rust`, `src/lib/fuchsia-sync`) build the
deps in file-level variables under `if (is_fuchsia)` and write `deps = LIB_DEPS`. It
also drops relative labels (`deps = [ "channel", "core" ]` in
`sdk/lib/driver/runtime/rust`), `proc_macro_deps`, and deps forwarded from a scope
(`src/storage/lib/vfs/rust`). So closure.py evaluates GN:

- **Evaluation** (`gn_eval.py`): assignments, `+=`/`-=`, `if`/`else if`/`else`, lists,
  scope literals (`common = { deps = [...] }`) with member access, `defined()`,
  `$var`/`${var}`/`${scope.member}` interpolation, `forward_variables_from` (from a
  known scope: copied), `foreach`, and **templates defined in the same file**, expanded
  with `invoker` and `target_name` as GN does (`rust_storage_trace` in
  `src/storage/lib/trace`). A call of an imported template is a target of that kind; its
  body is not run (these are the leaves: `fidl`, `zx_library`, …).
- **Fail-closed.** A value it cannot know (an imported variable, a function result) is
  UNKNOWN; a dep list entry that is UNKNOWN is counted in the target's `unknown_deps`,
  never followed. A construct it cannot follow — forwarding from an unknown scope (such
  as `invoker` of an imported template), a `foreach` over an unknown list, an assignment
  into a list element, a target whose name is not known, a leftover `$` form — is a
  recorded gap (`evaluation_gaps` in the report, with file, line and target) and, for
  forwarding, adds one to `unknown_deps`. `counts.unknown_deps` and
  `counts.evaluation_gaps` sum them. **The first version did not:** it evaluated scope
  literals to UNKNOWN and skipped `forward_variables_from` and `foreach` silently, which
  lost `vfs`'s forwarded deps (review finding 1, below).
- **Conditions per toolchain.** A crate built for Fuchsia is evaluated with
  `is_fuchsia = true`, `current_os = "fuchsia"`, `current_build_target_api_level =
  "HEAD"` (C3, R3), `is_kernel = false`; proc macros, their deps, and labels with an
  explicit `($toolchain)` are evaluated for the host (`is_host`, linux, x64,
  `PLATFORM`, M4). A condition on anything else (`current_cpu` for Fuchsia, which is
  both x64 and arm64) is UNKNOWN: both branches run, lists merge as a union (a target
  defined on both branches merges too), and the report lists it as `"unknown"`.
- **Build arguments** get their `declare_args()` defaults, read from the file itself and
  from its imports (one level), except where the overlay decides the value
  (`closure.OVERLAY_ARGS`, reported as `overlay_args`): `fuchsia_sync_detect_lock_cycles =
  false` (decided by the orchestrator after the review). A condition that reads one
  records the values per context in `build_args`.
- **Followed:** `deps`, `public_deps`, `non_rust_deps` and `proc_macro_deps` of
  `rustc_library`, `rustc_macro`, **`rustc_dylib`**, `rustc_staticlib`, `rustc_cdylib`,
  `rustc_binary` and `fuchsia_rust_driver`; `deps`/`public_deps` of `group`. Not
  followed: `test_deps` and test targets (D5).
- **FIDL bindings.** `<lib>_<flavor>` of a `fidl("<lib>")` target is a binding. What the
  binding templates add is modelled per flavor by `closure.FIDL_FLAVORS`, a table
  transcribed from `build/fidl/fidl.gni`, `build/rust/fidl_rust.gni` and
  `build/rust/fidl_rust_next.gni` at the revision (review finding 2): each flavor's Rust
  crate deps (`rust`/`rust_common`: `zx-status`, `fidl`, `bitflags`, `futures`, and `zx`
  for Fuchsia; `rust_next`/`rust_next_common`: `fidl_next_internal`,
  `static_assertions`), its sibling flavors (`rust` → `rust_common`, `rust_next` →
  `rust_next_common`, `rust_flex` → `rust`), the flavor its FIDL `public_deps` are taken
  in, and the driver deps a library with `contains_drivers` gets (`rust`: `fidl_driver`
  and `sdk/lib/driver/runtime/rust` when also `enable_rust_drivers`, not on the host;
  `rust_next`: `sdk/lib/driver/runtime/rust/fidl`). A FIDL `public_dep` on
  `//zircon/vdso/zx` becomes the `zx-types` crate, as the templates do. A flavor not in
  the table is a gap. The `//sdk/categories:marker-*` group every binding depends on is
  GN bookkeeping and is left out.
- **Other leaves:** `//third_party/rust_crates:<alias>` (crates.io), `<lib>_rust` of a
  `bind_library()` (bind library bindings), and any other template (native:
  `zx_library`, `sdk_shared_library`, …).
- **crates.io, transitively:** each direct alias is resolved through upstream's
  `third_party/rust_crates/vendor/BUILD.bazel` (the aliases regen.py uses; an alias it
  lacks is counted in `crates_io_direct_without_bazel_alias`), then upstream's
  crate_universe BUILD files are followed, as regen.py does in M5, but with `select()`
  branches limited to the platforms the overlay builds (both `*-unknown-fuchsia` and
  `x86_64-unknown-linux-gnu`, C5). Crates under `forks/` and `ask2patch/` are `patched`.
- **Upper bound.** The report also has `upper_bound_counts`: a second walk with every
  condition and build argument UNKNOWN (the brief's method), and what only it reaches.
- **Access (C1):** regen.py's `GitSource` (depth-1 blobless fetch into a temporary
  directory, blobs by ID, isolated git), one batched blob fetch per BFS level; about
  2 minutes per run. `--idk` marks FIDL/bind libraries present in an extracted IDK; the
  path itself is not written to the report.

### Report format (`docs/closure/pilot1.json`, `schema: 1`)

`counts`, `upper_bound_counts`, `overlay_args`; `intree` (per directory: `.rs` lines not
counting subpackages, whether upstream has a `BUILD.bazel`, and per target the GN
template, the same-file template it came from, crate type, crate name, edition, features,
toolchain contexts, `used_by` (every requester), `unknown_deps`); `crates_io.direct` (GN
alias, GN target, the Bazel alias's actual label, crate directory, contexts, `used_by`)
and `crates_io.transitive` (directory, name, version, patched, proc macro, build script,
SPDX license kinds, `in_cargo_lock`: a crates.io entry with a checksum in the release
`Cargo.lock`, false for the patched path crates); `fidl` (flavors, direct flavors, SDK
category, `contains_drivers`, in IDK), `bind`, `native`, `unresolved`, `conditionals`
(file, line, condition text, enclosing target, outcome and build arguments per context),
`evaluation_gaps`, `import_errors`. Lists are sorted, so reruns are byte-identical.

### Decision: split; `zx` goes to M6b

Accepted by the orchestrator. The direct count (44) does not exceed the rule by itself;
the transitive count (121 against M5's 6) and the new patched-crate mechanism make the
crates build too big for the rest of this session. `zx` alone (`closure.py
//sdk/rust/zx`: 5 in-tree crates, 12 crates.io crates, 6 not yet in `third_party/crates/`:
`bitflags`, `bstr`, `serde_core`, `static_assertions`, `ask2patch/memchr`,
`forks/libc-0.2.189`) needs exactly that mechanism: a committed tree for patched sources,
a local-source path in `toolchain/crates.bzl`, and new license texts (MIT, Unlicense).
That is the design-bearing half of M6b, better reviewed once with all four patched
crates, so `zx` was not "cheap" and is M6b's first step (plan entry).

## Limitations and open items

- Criteria 2–4 (the crates build) are M6b's.
- Imported templates are not run: their targets are leaves, and what they add is modelled
  only for the FIDL binding templates (`FIDL_FLAVORS`, transcribed by hand from the
  release; a later release that changes those templates needs the table updated — M14
  could check the three files' blob IDs). Other imported templates (`rustc_library`,
  `rustc_dylib`, …) could add deps of their own; they were not checked for that.
- Build arguments declared two imports deep are UNKNOWN (none were needed); the walk
  would report their conditions as UNKNOWN.
- `current_cpu` is UNKNOWN for Fuchsia (both targets), so a CPU-specific dep is counted
  for both; none occurs in pilot 1.
- A string whose substituted value itself contains `$` is conservatively UNKNOWN (the
  evaluator cannot tell it from a `$` form it does not read); none occurs in pilot 1.
- Deps of native (imported-template) leaves are counted, not followed
  (`native_deps_not_followed`, 28 for pilot 1, all C/C++; see "Native targets").
- The report is a snapshot at the lock's revision; regenerating it is manual until M14.

### How the walker differs from the brief's

The brief's App. B walker matches `deps = [ ... ]` with regular expressions inside the
target's block. At this revision that misses whole files: bazel2gn-generated BUILD.gn
files (for example `src/lib/diagnostics/log/rust`, `src/lib/fuchsia-sync`) build the
deps in file-level variables under `if (is_fuchsia)` and write `deps = LIB_DEPS`. It
also drops relative labels (`deps = [ "channel", "core" ]` in
`sdk/lib/driver/runtime/rust`) and `proc_macro_deps`. So closure.py evaluates GN:

- **Evaluation.** `gn_eval.py` runs assignments, `+=`/`-=`, `if`/`else if`/`else`,
  lists, `$var`/`${var}` interpolation and `defined()`; a call with a block is a target
  of that kind (templates and imports are not run). Anything it cannot know (an
  imported variable, a function result, scope access) is UNKNOWN.
- **Conditions per toolchain.** A crate built for Fuchsia is evaluated with
  `is_fuchsia = true`, `current_os = "fuchsia"`, `current_build_target_api_level =
  "HEAD"` (C3, R3), `is_kernel = false`; proc macros, their deps, and labels with an
  explicit `($toolchain)` are evaluated for the host (`is_host`, linux, x64,
  `PLATFORM`, M4). A condition on anything else (`current_cpu` for Fuchsia, which is
  both x64 and arm64) is UNKNOWN: both branches run and lists merge as a union, and the
  report lists it as `"unknown"`.
- **Build arguments** get their `declare_args()` defaults, read from the file's own
  imports (one level); a condition that reads one records it in `build_args`.
- **Followed:** `deps`, `public_deps`, `non_rust_deps` and `proc_macro_deps` of
  `rustc_library`, `rustc_macro`, **`rustc_dylib`**, `rustc_staticlib`, `rustc_cdylib`,
  `rustc_binary` and `fuchsia_rust_driver`; `deps`/`public_deps` of `group`. Not
  followed: `test_deps` and test targets (D5).
- **Leaves:** `//third_party/rust_crates:<alias>` (crates.io), `<lib>_<flavor>` of a
  `fidl("<lib>")` target (FIDL bindings; the library's own FIDL deps are then followed
  with the same flavor), `<lib>_rust` of a `bind_library()` (bind library bindings),
  and any other template (native: `zx_library`, `sdk_shared_library`, …).
- **crates.io, transitively:** each direct alias is resolved through upstream's
  `third_party/rust_crates/vendor/BUILD.bazel` (the aliases regen.py uses), then
  upstream's crate_universe BUILD files are followed, as regen.py does in M5, but with
  `select()` branches limited to the platforms the overlay builds (both
  `*-unknown-fuchsia` and `x86_64-unknown-linux-gnu`, C5). Crates under `forks/` and
  `ask2patch/` are marked `patched`.
- **Upper bound.** The report also has `upper_bound_counts`: a second walk with every
  condition and build argument UNKNOWN (the brief's method), and what only it reaches.
- **Access (C1):** regen.py's `GitSource` (depth-1 blobless fetch into a temporary
  directory, blobs by ID, isolated git), one batched blob fetch per BFS level; about
  90 s per run. `--idk` marks FIDL/bind libraries present in an extracted IDK; the path
  itself is not written to the report.

### Report format (`docs/closure/pilot1.json`, `schema: 1`)

`counts`, `upper_bound_counts`; `intree` (per directory: `.rs` lines not counting
subpackages, whether upstream has a `BUILD.bazel`, and per target the GN template,
crate type, crate name, edition, features, toolchain contexts, `used_by`);
`crates_io.direct` (GN alias, GN target, the Bazel alias's actual label, crate
directory, contexts, `used_by`) and `crates_io.transitive` (directory, name, version,
patched, proc macro, build script, SPDX license kinds, `in_cargo_lock`: a crates.io
entry with a checksum in the release `Cargo.lock`, false for the patched path crates); `fidl`
(flavors, direct flavors, SDK category, in IDK), `bind`, `native`, `unresolved`,
`conditionals` (file, line, condition text, enclosing target, outcome per context, build
arguments read), `import_errors`. Lists are sorted, so reruns are byte-identical.

### Decision: split; `zx` goes to M6b

45 > 44 direct crates, and 124 crates transitively against M5's 6. `zx` alone
(`closure.py //sdk/rust/zx`: 5 in-tree crates, 12 crates.io crates, 6 not yet in

step (plan entry).

## Limitations and open items

- Criteria 2–4 (the crates build) are M6b's.
- The evaluator does not run templates or nested imports: a target defined through a
  template in the same file keeps the template's name as its kind (pilot 1 has none),
  and build arguments declared two imports deep are UNKNOWN (none were needed).
- `current_cpu` is UNKNOWN for Fuchsia (both targets), so a CPU-specific dep would be
  counted for both; none occurs in pilot 1.
- The report is a snapshot at the lock's revision; regenerating it is manual until M14.

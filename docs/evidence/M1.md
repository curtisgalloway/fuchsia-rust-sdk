### Implementation steps
1. Add `LICENSE` (Apache-2.0), `README.md` (one paragraph plus a link to
   design/plan), `.gitignore` (`bazel-*`, `.dev/`, `__pycache__`), and `pyproject.toml`
   for `uv` with `pytest` as a dev dependency. All carry SPDX headers.
2. `scripts/resolve_pins.py <sdk-version> [--out overlay.lock.json]`, with these steps:
   1. Get the revision by the I1 method (`evidence/I1.md` "Method"), and record the
      integration commit too. Keep the all-builds-agree check. One integration
      commit does not fix `fuchsia.git` (`20.20240404.1.1`), and the IDK's own build
      is not among those checked, so the FIDL-blob cross-check in I1 is the only
      direct evidence about the IDK itself.
   2. Fetch `manifests/toolchain` at that revision: `git fetch --depth 1` of that
      commit with a sparse, blobless checkout, or `git archive`-style reads through
      git. Never gitiles.
   3. Parse the two Rust packages and their `git_revisions:` version.
   4. Resolve instance IDs with CIPD `ResolveVersion` (brief App. B step 3). The host
      package is resolved for `linux-amd64`.
   5. Pin the Bazel SDK from this release's own artifacts (decided by the
      orchestrator 2026-09-27):
      - the IDK `core.tar.gz` from `gs://fuchsia/development/<V>/sdk/linux-amd64/`,
        pinned by SHA-256;
      - `fuchsia/development/rules_fuchsia` from CIPD, resolved by
        `git_revision:<integration_revision>`.

      Never pin a Bazel SDK instance from another release (C3). At
      `33.20260927.4.1`, `fuchsia/sdk/core/fuchsia-bazel-rules/linux-amd64` has no
      instance (a publishing gap; see I1 evidence). If that package later gains
      `version:<V>` for the same release, M1 may use it instead and record why.
   6. Take the SHA-256 of `third_party/rust_crates/Cargo.lock` at the revision.
   7. Write the lock with sorted keys and a trailing newline, via temp file then
      `os.replace`.
3. The lock schema has one object per field, each with `value` and `source` (the URL
   or git path it came from, per R1). Proposed keys: `sdk_version`, `fuchsia_revision`,
   `integration_revision`, `rust_host`, `rust_target`, `bazel_sdk`, `rules_fuchsia`,
   `cargo_lock_sha256`.
4. `tests/test_resolve_pins.py`: HTTP and git are stubbed behind one small interface.
5. Commit `overlay.lock.json` for `33.20260927.4.1`.

## Decisions this milestone rests on

- **Bazel SDK pin (orchestrator, 2026-09-27, plan step 2.5):** "the lock pins the Bazel

  `gs://fuchsia/development/<V>/sdk/linux-amd64/` by SHA-256, plus
  `fuchsia/development/rules_fuchsia` from CIPD resolved by the release's integration
  `git_revision`; never a Bazel SDK instance from another release (C3). If
  `fuchsia/sdk/core/fuchsia-bazel-rules/linux-amd64` gains `version:<V>` for the same
  release, you may use it instead, recording why." Re-checked 2026-09-27: that package
  still answers 404 `no such tag` for `version:33.20260927.4.1`, so the decision applies
  as written and `resolve_pins.py` does not consult it.
- **`integration_revision` is a lock key** (plan step 3; I1 review finding 4).
- **License check (orchestrator):** "choose `reuse lint` via `uvx reuse lint` if it works
  offline-enough here, else a small script; record the choice. … make the check pass
  for the repo as it is, without editing the brief's content beyond its header if
  needed." Chosen: `reuse lint` (reuse 6.2.0), pinned as a `dev` dependency in

Decisions made in this milestone (each has a notebook `decision` entry):

- **Schema:** every field is `{"value": …, "source": [ … ]}`, and `source` is always a
  list, because the two revisions rest on several artifacts that must agree. CIPD fields
  add `package`, and `bazel_sdk` adds `url` (review finding 5), so M2 need not parse
  either from a source string.
- **Source notation:** GCS and CIPD sources are HTTPS URLs; CIPD uses the package's
  public `…/p/<package>/+/<tag>` name. Git sources are `<repo> <revision>:<path>`, the
  revspec `git cat-file -p` takes. Gitiles URL forms are deliberately not used, even
  as names.
- **`rules_fuchsia` cross-check:** resolved by `git_revision:<integration_revision>` as
  decided. When `version:<V>` also resolves, it must name the same instance, or the run
  fails. A 404 on `version:<V>` is accepted; any other error fails.
- **IDK integrity:** GCS publishes no SHA-256 for `core.tar.gz`, so the resolver streams
  it (about 50 s, 3,012,334,939 bytes, never written to disk) and checks size and MD5
  against the GCS JSON API metadata in the same pass.
- **Reading files at a commit:** `git init --bare`, `git fetch --depth 1
  --filter=blob:none <fuchsia.git> <revision>`, then `git cat-file -p <revision>:<path>`,
  which fetches only the two blobs asked for (about 5 MB and 20 s in all). No sparse
  checkout is needed. The commit is fetched once per run, and each path is read on its
  own, so a failure names the field that needs that file.
- **No credentials (C1), after review finding 1:** git runs with no system or global
  config (`GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`), an empty temporary
  `HOME` and `XDG_CONFIG_HOME` (so curl inside git reads no `~/.netrc`), every inherited
  `GIT_*` variable dropped except `GIT_SSL_CAINFO`/`GIT_SSL_CAPATH` (CA trust only; this
  also drops `GIT_CONFIG_COUNT`/`GIT_CONFIG_PARAMETERS` injection), no `SSH_ASKPASS`,
  and `-c credential.helper= -c http.cookieFile= -c core.askPass=`,
  `GIT_TERMINAL_PROMPT=0`. urllib sends no credentials: the resolver installs no auth
  handler, and `urllib.request` has no netrc code (`inspect.getsource(urllib.request)`
  has no mention of it). Proxy variables are kept; they are the container's egress
  path and carry no upstream credentials.

## Limitations and blockers

- **I1's limitation carries over.** The revision rests on the product builds agreeing
  and on the integration commit linking them to the IDK. The IDK's own build is not
  checked, and I1's FIDL-blob cross-check is not repeated per run.
- **Each run streams the 3 GB IDK** to hash it, about 50 s here. That is acceptable for
  a per-release tool; `regen.py` (M14) may want to skip it when the lock already
  matches.
- **`rules_fuchsia` instances are shared across releases.** `8d346b9a…` carries 18
  `version` tags (`33.20260925.6.1` to `33.20260928.0.1`), because CIPD deduplicates
  identical content. The pin is still this release's (resolved by its integration
  commit), but it does not by itself show the rules differ from a neighbor's.
- **A failure to fetch the commit is reported under `rust_host`,** the first field
  that needs its files. A failure reading one file names that file's field.
- **The IDK URL is not pinned to a GCS generation.** The SHA-256 pins the content, so a
  replaced object would fail M2's download check rather than build silently.
- No Bazel files yet (out of scope); M2 consumes `rust_host`, `rust_target`,
  `bazel_sdk` and `rules_fuchsia`.

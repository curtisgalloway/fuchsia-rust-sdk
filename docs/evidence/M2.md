## Milestone definition (moved from the plan)

**Design coverage:** I5, R2 (link half), D3, D4, C5, A2.
**Dependencies:** M1.
**In scope:**
- `MODULE.bazel` and `.bazelversion`, with Bazel matching the release's
  `sdk-samples/drivers`.
- `rules_fuchsia` + `@fuchsia_sdk` at the lock's version.
- `rules_rust` 0.69.0 with upstream's patch in `patches/rules_rust/`.
- `toolchain/`: a CIPD repository rule, plus `rust_toolchain()` targets for
  `x86_64-unknown-fuchsia`, `aarch64-unknown-fuchsia` and host.
- `.bazelrc` with `fuchsia_x64` / `fuchsia_arm64` configs.
- `examples/hello_rust/` (proposed): a `rust_binary` that calls into `libfdio.so`.

**Out of scope:** running on a device (M3); `rustc_*` wrappers (M4); any vendored crate
(M5).

### Implementation steps
1. **I5 first:** an empty workspace with both rule sets that resolves `@fuchsia_clang`
   and `@fuchsia_sdk`. Record the Bazel version and any `MODULE.bazel` conflicts.
   `fuchsia-cloud-dev/MODULE.bazel` is a working reference for the `rules_fuchsia`
   half.
2. Copy upstream's `rules_rust` patch from `fuchsia.git` at the lock revision (path from
   brief §3.4) with its license header. Apply it via `single_version_override(patches=…)`.
3. `toolchain/cipd.bzl` (proposed): a repository rule that downloads a CIPD instance by
   ID over anonymous HTTPS, then checks it by the content hash the instance ID encodes.
4. `toolchain/BUILD.bazel`: port `build/bazel/toolchains/rust/rust.BUILD.bazel`, and
   link through `@fuchsia_clang` with `@fuchsia_sdk//pkg/sysroot`.
5. Build `hello_rust` under both configs, and read its `DT_NEEDED` with `llvm-readelf`
   from `@fuchsia_clang`.

## Decisions this milestone rests on

- **Bazel SDK source (orchestrator, 2026-09-27):** "Bazel SDK from the release's own IDK
  `core.tar.gz` (lock `bazel_sdk.url` + sha256) plus `rules_fuchsia` CIPD instance from
  the lock; never another release's instance (C3). The lock is the only per-release
  input: Bazel must not fetch anything per-release that isn't pinned there (if you need a
  new pin, e.g. the Bazel binary itself, either pin it in the repo in a way M14's regen
  can refresh, or extend the lock via resolve_pins.py with tests — record which and
  why)."
- **Design D3:** upstream's pinned CIPD Rust toolchain (not rustup). **D4:** both x64
  and arm64.
- **Config names:** `fuchsia_x64` / `fuchsia_arm64` as the plan proposes (kept; no reason
  to change).

Decisions made in this milestone (each has a notebook `decision` or `dead end` entry):

- **Two new lock fields, from `resolve_pins.py` (with tests).** `rust_host_std`
  (`fuchsia/third_party/rust/target/x86_64-unknown-linux-gnu`) and `clang`
  (`fuchsia/third_party/clang/linux-amd64`), both read from the release's
  `manifests/toolchain` like `rust_host`/`rust_target`. Why: the host Rust package has
  no host `std` (only `lib/rustlib/x86_64-unknown-linux-gnu/bin/rust-objcopy`), so proc
  macros and host tools need upstream's separate host-std package; and `@fuchsia_clang`
  had no pin at all. `resolve_pins.py` now also fails if the three Rust packages are not
  pinned at the same `git_revisions:` (std must match the compiler build).
- **Bazel 8.5.1, pinned in the repo, not the lock.** `.bazelversion` plus
  `scripts/bazel.sha256`; `scripts/bazel` downloads the official GitHub release once and
  checks it. The value is fuchsia.git's own pin at the lock revision
  (`manifests/jiri.lock`: `fuchsia/third_party/3pp/bazel/linux-amd64`
  `version:2@8.5.1.8`, whose `bazel-real` is byte-identical to GitHub's 8.5.1,
  SHA-256 `61d89402…`). Not a lock field in M2 because M14's regen owns release bumps;
  it could become one (it is derivable from the revision), see open items.
  **This deviates from design §4.1/§8.1 ("matches sdk-samples/drivers").** Reason:
  sdk-samples/drivers pins Bazel 8.1.0 (through `fuchsia-infra-bazel-rules` `127a22ce`,
  CIPD `bazel_bootstrap`, byte-identical to GitHub's 8.1.0), and 8.1.0 cannot analyze
  this release's generated `@fuchsia_sdk` (native `cc_import` has no
  `strip_include_prefix`). sdk-samples/drivers itself is still on SDK
  `32.20260626.7.1`, so it never met this SDK. A2 is therefore false as worded; see
  "Question for the owner".
- **`rules_cc` 0.2.19**, fuchsia.git's pin at the revision, not
  `fuchsia-infra-bazel-rules`' 0.2.14 (tried while diagnosing the `cc_import` failure;
  kept because it matches upstream; other BCR versions follow
  `fuchsia-infra-bazel-rules`).
- **Two module extensions.** `lock_repos` (`toolchain/repositories.bzl`) creates
  `rules_fuchsia`, `fuchsia_idk` and `fuchsia_rust_toolchain` from the lock.
  `fuchsia_repos` (`toolchain/fuchsia.bzl`) loads rules_fuchsia's own
  `fuchsia_clang_repository`, `fuchsia_sdk_repository` and `fuchsia_toolchain_decl`, so
  `@fuchsia_sdk` is generated from the IDK exactly as rules_fuchsia intends and clang is
  fetched by rules_fuchsia's code path (`cipd_tag` = instance ID, `sha256` checked).
  Nothing in `MODULE.bazel` names a release.
- **CIPD by instance ID over `/dl/`.** CIPD's `/dl/<package>/+/<id>` accepts the
  base64url instance ID, not the hex digest the lock stores; `toolchain/lock.bzl`
  computes the ID (unpadded base64url of digest ‖ `0x02`) and passes the hex digest as
  `sha256` to `download_and_extract`, so ID and hash name the same bytes.
- **Toolchain port as the repository's BUILD file.** `toolchain/rust.BUILD.bazel` is
  upstream's `rust.BUILD.bazel` with the changes listed in its header (fixed linux-x64
  host, no linux-arm64/riscv64, `rust_toolchain_with_build_flags` from `@rules_fuchsia`,
  no API-level flags until M4); verified by `diff -u` against upstream at `b5274053`.
  Kept under upstream's BSD-3-Clause notice plus SPDX lines (C4);
  `LICENSES/BSD-3-Clause.txt` is fuchsia.git's `LICENSE`.
- **API level.** `.bazelrc`: `--default_fuchsia_api_level=HEAD` (as sdk-samples) and, in
  the Fuchsia configs, `--override_fuchsia_api_level=HEAD`: bare `rules_rust` targets get
  no `fuchsia_transition`, and the generated SDK's `cc_import`s select on the level.
- **Host linking** uses the autodetected system C toolchain (`/usr/bin/gcc`); see
  limitations.

## Deviations from the plan text

- **Bazel version:** 8.5.1 (fuchsia.git's pin), not sdk-samples/drivers' 8.1.0 (above).
- **`toolchain/BUILD.bazel`** holds only an `exports_files`; the port is
  `toolchain/rust.BUILD.bazel`, installed as the toolchain repository's BUILD file, as
  upstream installs its own. Plan step 3's `cipd.bzl` is
  `lock.bzl` + `repositories.bzl`.
- **Lock schema grew** by `rust_host_std` and `clang` (orchestrator allowed this, with
  tests).
- **`examples/hello_host/`** added for criterion 4 (the plan named no path).

## Question for the owner

**Design §4.1 and A2 name sdk-samples/drivers as the source of the Bazel version. That
does not hold for this release** (8.1.0 cannot analyze its SDK; sdk-samples/drivers is on
SDK 32). Recommendation: amend the design to "the Bazel that fuchsia.git pins at the
release revision" (`manifests/jiri.lock`), which is tied to the release, is the version
upstream tests `rules_rust` 0.69.0 + patch with, and could be resolved by
`resolve_pins.py` in M14. M2 uses 8.5.1 on that basis.

## Limitations and open items

- **Disk (blocks M3 as planned).** About 20 GB for the Bazel caches, 9 GB free. Options
  for the orchestrator/owner: trim the IDK in `idk_repository` (e.g. drop `obj/` levels
  other than the target level and riscv64; needs a check that the generated SDK
  tolerates it), delete the repository cache after fetching (costs a 3 GB re-download
  on any refetch), or run emulator milestones in a larger environment.
- **Host C toolchain is the system's** (`/usr/bin/gcc` via rules_cc autodetection), so
  host binaries and proc macros link non-hermetically. Upstream links with its clang.
- **Linker warning** on every Fuchsia link: `clang: warning: argument unused during
  compilation: '-pie'` (from the cc toolchain's link flags; `linker_messages` is not
  denied by `-Dwarnings`). Harmless; noisy.
- **Host-only Rust targets need `target_compatible_with = ["@platforms//os:linux"]`**,
  or `//...` under a Fuchsia config builds them for Fuchsia (seen with the proc macro).
- **Not run:** the binaries on a device (M3).

## Investigation definition (moved from the plan)

**Design coverage:** I3 (blocks R8a's "binds"). **Dependencies:** M3.
**Lead (found 2026-09-27, not yet verified at this release):**
`fuchsia-cloud-dev`'s `qemu_edu` driver binds on `core.x64` `33.20260919.6.1` under TCG
with this rule:

```
composite qemu_edu;
using fuchsia.acpi;
using fuchsia.pci;
primary parent "pci" { fuchsia.BIND_PCI_VID == 0x1234; fuchsia.BIND_PCI_DID == 0x11e8; }
optional parent "acpi" { fuchsia.BIND_PROTOCOL == fuchsia.acpi.BIND_PROTOCOL.DEVICE; }
```

The PCI bus publishes composite node specs, so a non-composite rule registers but never
binds. Both bind libraries are in the SDK.
**Evidence to collect:** at the lock's release, confirm the edu device appears
(`ffx driver list-devices -v`, with the QEMU `-device edu` flag used by
`fuchsia-cloud-dev`), and that the rule above still compiles against this IDK's bind
libraries.
**Exit:** a `.bind` file for `drivers/simple_rust`, using only IDK bind libraries, plus
the emulator command line that adds the device, both recorded in `docs/evidence/I3.md`.
**Note for M11:** the edu device is owned by no in-tree driver on `core.x64`. If
`qemu_edu` from `fuchsia-cloud-dev` is also registered, the two compete; register only
the pilot.

The orchestrator's task for this session added: switch the pilot's bind rule from M10's
placeholder to the new file (so the package builds with it), keep the driver source
unchanged, and optionally check the bytecode against the node's properties without
registering.

## Answer

The lead holds at `33.20260927.4.1`. `scripts/emu start` adds the device (`-device edu`);
`core.x64` publishes it as `PCI0.bus.00_06_0` and a two-parent composite node spec
`00_06_0` (`pci` + `acpi`), which no driver matches. The lead's rule, as
`drivers/simple_rust/meta/simple_rust.bind` (composite name `simple_rust`), compiles with
the IDK's `bindc` against the IDK's `fuchsia.acpi` and `fuchsia.pci`, lint-clean, and
`bindc test` matches it against both parents' properties as the emulator reports them.
The pilot now builds with it for x64 and arm64 (`meta/placeholder.bind` is gone), and a
new `//drivers/simple_rust:bind_test` re-runs that check in `bazel test`. The driver
source is unchanged and needs nothing more to bind (below).

### `bind_test` in Bazel, and why not `rules_fuchsia`'s rule

`rules_fuchsia` has `fuchsia_driver_bind_bytecode_test`, but at this release it fails:

```
run_bind_test.sh: line 2: external/+fuchsia_repos+fuchsia_sdk/tools/x64/bindc: No such file or directory
```

Its script names `bindc`, the rules and the include files by `File.path` (execroot
paths, `external/<repo>/...`), which do not exist in the runfiles tree under Bzlmod, and
`bindc` is not in its runfiles. `rules/bind_test.bzl` (`fuchsia_driver_bind_test`) runs
the same command by `short_path` from the runfiles (the SDK toolchain's `bindc`, the deps'
`FuchsiaBindLibraryInfo.transitive_sources`); the rules file precedes `--include`, which
takes every value after it (first attempt: "The test command requires an input.").
Fuchsia-only through its deps, so host `bazel test //...` skips it.

### The `elf_test` flake (M10's test, fixed here)

The first x64 test run also failed `elf_test`: `FAIL: lib/libfdio.so is not for X86-64`
(and `lib/libsvc.so`). Alone it passed three times; `--runs_per_test=40 --nocache_test_results`
failed 36 of 40, each run naming random packaged files (all seven seen). Cause: under
`set -o pipefail`, `"$readelf" --file-header "$path" | grep -q ...` fails when `grep -q`
exits at the match and `readelf`'s next write gets SIGPIPE. The script now captures the
header first. After: `--runs_per_test=40` all pass. `rules/` was otherwise unchanged since
`2a63354`; this is in its own WIP commit.

## Findings for M11

- **Driver source: no change needed to bind.** The source reads no property of its
  parent; it only sets `bind_fuchsia_test::TEST_CHILD = "simple"` on the child node it
  adds, so it keeps `//drivers/bind:fuchsia.test_rust` (a Rust crate dependency, not a
  bind input). The bind rule no longer uses `fuchsia.test`. A composite driver receives
  the composite node through the same `DriverContext::take_node`; `virtio-gpu-display`
  (pure Rust) runs that way on this image.
- **Manifest:** upstream's `.cml` has no `colocate` and no `device_categories`. Without
  `colocate`, the composite driver should get its own driver host (DFv2's default);
  that is where M11 will see whether the packaged `libdriver_runtime.so` is used or the
  host's (M10's "two copies" item). `static-checks` flags the missing
  `device_categories`; whether that blocks anything is for M11 to observe.
- **Replay:** `scripts/emu start` → `scripts/emu driver //drivers/simple_rust:pkg` →
  `ffx driver composite show 00_06_0` should then name `simple_rust_driver`'s URL and a
  composite node `PCI0.bus.00_06_0.00_06_0` (by analogy with `00_04_0`), and
  `list-devices -v` should show it bound. Register only the pilot (the plan's note).
- **Release bumps:** if a later `core.x64` changes the spec's properties, `bind_test`'s
  JSON is the place to update, from `ffx driver composite show 00_06_0`.

## Limitations

- The rule is verified against the properties the emulator reports, by `bindc`'s own
  evaluator; binding on the target is M11's (nothing was registered here).
- `ffx driver static-checks` reports the missing `device_categories` (upstream's
  manifest); not changed.
- `rules_fuchsia`'s `fuchsia_driver_bind_bytecode_test` is not usable under Bzlmod at this
  release (backlog); the overlay's rule replaces it.

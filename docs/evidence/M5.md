### Implementation steps
1. Git access: sparse, blobless fetch of `fuchsia.git` at `fuchsia_revision` into a
   scratch directory outside the repo (brief App. B step 1).
2. Copy each listed crate directory to `vendor/fuchsia/<upstream path>/` (D9).
3. For crates with upstream `BUILD.bazel`, rewrite labels:
   - `//<path>` → `//vendor/fuchsia/<path>`
   - `//third_party/rust_crates:<x>` → the crate-universe label
   - upstream rule loads → `//rules:rustc.bzl`
   - `//build/config/rust/lints:<x>` → `//rules/lints:<x>` (10 upstream files pass
     `lint_config = "//build/config/rust/lints:clippy_warn_all"`; M4 review finding 3)
   - every `rustc_*` target gets `vendored = True` (decided after M4 review finding 2:
     the overlay builds upstream code at HEAD, which upstream builds at PLATFORM, with
     `-Dwarnings` and `unused_crate_dependencies = warn`; its lints are upstream's
     concern)

   Otherwise, copy `overlays/<path>/BUILD.bazel`.
4. Apply `patches/fuchsia/<path>/*.patch` in order. A failing patch stops the run and
   names the patch and the file.
5. `--check`: regenerate into scratch and diff against `vendor/`; exit non-zero on drift.
6. pytest for label rewriting, patch failure and drift detection, using a tiny fake
   upstream tree.

### How `regen.py vendor` works

1. Reads `fuchsia_revision` and `cargo_lock_sha256` from `overlay.lock.json`, and
   `vendor/crates.txt`. Overlays or patches for unlisted paths, and an overlay for a
   crate listed `upstream`, fail the run.
2. **Git (C1):** in a temporary directory, `git init --bare`, one
   `fetch --depth 1 --filter=blob:none <fuchsia.git> <revision>` (checked against
   `FETCH_HEAD`), `ls-tree` for the listed paths, then one
   `fetch <blob-oid>…` for all needed blobs and `cat-file --batch`. git runs through
   `resolve_pins.isolated_git` (no system/global config, empty HOME, no credential
   helper, cookie file or askpass, no inherited `GIT_*`), the path M1's review
   hardened and tested with a hostile HOME. About 16 s end to end; the scratch
   repository (about 5 MB) is deleted afterwards. Nothing git-related runs at build
   time.
3. Copies each directory byte for byte with its mode, leaving out subdirectories that
   are packages of their own (`BUILD.bazel`/`BUILD.gn`). Copies the root `LICENSE` and
   `PATENTS`, writes `vendor/fuchsia/BUILD.bazel` (the `license` target).
4. `BUILD.bazel`: `upstream` → rewritten (below), with a two-line header naming the
   source blob above upstream's own header; `overlay` → `overlays/<path>/BUILD.bazel`
   copied, after checking every `rustc_*` call in it sets `vendored = True`.
5. Applies `patches/fuchsia/<path>/*.patch` in name order with `git apply`, relative to
   the fuchsia.git root, in the staging tree (`GIT_CEILING_DIRECTORIES` keeps git from
   finding an enclosing repository). A patch may touch only files of its own `<path>`
   (checked with `--numstat` first). A failure names the patch and the file.
6. **crates.io subset:** every `@rust_crates//vendor:<x>` in the generated BUILD files is
   looked up in upstream's `third_party/rust_crates/vendor/BUILD.bazel`; the closure is
   followed through upstream's generated per-crate `BUILD.bazel` files (one blob fetch
   per level). Each crate's `package_info` (name, version) must match its directory and
   a crates.io entry in the release's `Cargo.lock`, whose SHA-256 must equal the lock's
   `cargo_lock_sha256`. Labels are rewritten to `//vendor/<crate>:<t>` inside
   `@rust_crates`. A label into `forks/`, `ask2patch/` or any other non-`vendor/` path
   fails the run ("patched and forked crates come in milestone M6").
7. `vendor`: replaces `vendor/fuchsia/` and `third_party/crates/` wholesale (stale files
   disappear). `--check`: compares both trees with the fresh output, file by file
   (content and executable bit), and prints one line per missing, extra or differing
   file; exit 1 on drift, 2 on an input error, 0 when clean.

**Label map (upstream in-tree `BUILD.bazel`; strings only, comments untouched):**

| Upstream | Overlay |
|---|---|
| `//build/bazel/rules/rust:defs.bzl` | `//rules:rustc.bzl` (loading anything but the three `rustc_*` macros fails) |
| `//build/config/rust/lints:<x>` | `//rules/lints:<x>` |
| `//:license` | `//vendor/fuchsia:license` |
| `//third_party/rust_crates/vendor:<x>` | `@rust_crates//vendor:<x>` |
| `//<path>[:t]`, `<path>` listed | `//vendor/fuchsia/<path>[:t]` |
| `//visibility:*`, `//conditions:*`, `@repo//…`, `:t` | unchanged |
| anything else (`//build/…`, unlisted paths, patched crates) | error naming file, label and reason |

Every `rustc_library`/`rustc_binary`/`rustc_proc_macro` call gets `vendored = True` as its
first argument (with a `# Generated by scripts/regen.py` comment); a call that already
sets `vendored` fails (use an overlay).

### Decisions (details in the notebook)

1. **`zx` deferred to M6.** Its crates.io deps include two patched crates: `libc`
   (upstream builds `forks/libc-0.2.189`) and `memchr` (reached through `bstr`'s
   `BUILD.bazel`, `ask2patch/memchr`). Bringing patched crates in "as local repositories
   from `third_party/rust_crates/`" is M6's scope and a design choice: fetching
   fuchsia.git at build time is what D6 rejected, and committing their sources is new.
   Upstream's unified `bitflags` features would also pull `serde_core`. `zx-status` and
   `zx-status-ext` (only `zx-types` below them) are vendored now, so M6 adds `zx` alone
   plus its crates.
2. **The smallest crates.io subset, without running crate_universe.** `zx-types` needs
   `zerocopy` with its derive macros, so M5 needs crates.io regardless. Upstream already
   ran crate_universe over this release's `Cargo.toml`/`Cargo.lock` and committed the
   output; regen.py reuses those generated BUILD files (same features, cfgs and build
   scripts as upstream) and takes each crate's `.crate` from static.crates.io, pinned by
   the release `Cargo.lock`'s SHA-256 (C1, C3). The closure is 6 crates: `zerocopy`
   0.8.48, `zerocopy-derive` 0.8.48, `proc-macro2` 1.0.107, `quote` 1.0.47, `syn`
   2.0.119, `unicode-ident` 1.0.19. No `crate_universe` or cargo-bazel download, no
   index access, `MODULE.bazel.lock` unchanged. M6 may keep this (and extend it for
   patched crates) or replace it with its own crate_universe run.
3. **One `@rust_crates` repository** laid out as upstream's `third_party/rust_crates`
   (`vendor:<alias>`, `vendor/<crate>-<version>:<target>`), so labels map by prefix. It
   downloads all listed crates when first needed (7.4 MB now); per-crate repositories
   can come with M6's larger set if that matters.
4. **LICENSE at `vendor/fuchsia/`, not in each crate.** Upstream crates have no
   `LICENSE` of their own; the root one covers them and every header points to it.
   `vendor/fuchsia/` is that root for the vendored subset (D9), so it carries the root
   `LICENSE` and `PATENTS`; the `license` target names it. Adding a non-upstream
   `LICENSE` file to each crate would break "byte-for-byte upstream" for no legal gain.
5. **Generated root `BUILD.bazel`** in `vendor/fuchsia/` for `//:license`, with
   `license_kinds` BSD-3-Clause where upstream's `toplevel.BUILD.bazel` says BSD-2-Clause
   (the LICENSE text is the 3-clause one); marked "Overlay:" in the file.
6. **Inputs outside the generated tree.** `vendor/crates.txt` is an input beside
   `vendor/fuchsia/` (the plan's proposed path); regen.py owns only `vendor/fuchsia/` and
   `third_party/crates/`.
7. **`.bazelignore`** for `overlays/`, so hand-written overlay `BUILD.bazel` files are not
   packages in place (verified: a deliberately broken `overlays/x/BUILD.bazel` does not
   affect `bazel query //...`).

## Deviations from the plan text

- **`zx` does not build yet** (allowed by the criterion): deferred to M6, decision 1.
- **Git access is not a sparse checkout** (plan step 1 cites brief App. B's sparse
  clone): a depth-1 blobless fetch plus one by-ID fetch of exactly the needed blobs gets
  the same files with no working tree, and reuses M1's isolated git.
- **No crate_universe run** (design §4.2 "Third-party crates" says crate_universe is run
  over the release's `Cargo.toml`/`Cargo.lock`): upstream's own crate_universe output is
  reused, decision 2. If M6 keeps this route, the orchestrator may want to amend §4.2's
  wording.
- **`third_party/crates/` is created in M5** (the plan put the crates.io repository in
  M6), as the smallest subset `zx-types` needs; regen.py's vendor stage writes it and
  `--check` covers it.
- **Two extra crates**, `zx-status` and `zx-status-ext`: vendored now because `zx`
  needs them and they build with what M5 has.

## Limitations and open items

- `zx` waits for M6: it needs `libc` (fork), `memchr` (ask2patch, via `bstr`),
  `bitflags` (+ `serde_core` under upstream's features) and `static_assertions`.
- `regen.py --check` needs network access to fuchsia.git (it regenerates from upstream);
  about 16 s.
- Crates.io crates get upstream's Fuchsia-wide unified features (e.g. `zerocopy`'s
  `simd`, `std`), not the minimum the closure needs; this matches how upstream builds
  them.
- The closure follows every label in an upstream crate BUILD file, including
  `select()` branches for platforms the overlay does not build; with more crates this
  can fetch crates that are never compiled (none now).
- `@rust_crates` is one repository: any use downloads all listed crates.
- `tests/vendor/BUILD.bazel` lists the vendored crates by hand; add each new one.
- Nested crates (a listed path inside another listed path) are copied as separate
  packages; not exercised by the real crates yet (M9's `sdk/lib/driver/runtime/rust/*`
  will).

## Milestone definition (moved from the plan)

**Design coverage:** R3. **Dependencies:** M2.
**In scope:**
- `rules/rustc.bzl`: `rustc_library`, `rustc_proc_macro` and `rustc_binary` wrappers
  over `rules_rust`, ported from upstream `build/bazel/rules/rust/`.
- `--cap-lints` for vendored code.
- API-level cfg generation from the IDK's `version_history.json`, targeting `HEAD`.
- `tests/api_level/`, a test crate.

**Out of scope:** the test wrapper (`rustc_test`, R9 → M16); the driver rule.

### Implementation steps
1. Port `rustc_api_level.bzl`. The input is `version_history.json` from
   `@fuchsia_sdk`. Emit `--cfg=fuchsia_api_level_at_least="N"` for every supported
   level ≤ target, and `…_less_than` for the rest, exactly as upstream does. Record
   the upstream file and revision in a header comment.
2. Wrappers apply cfgs, edition default, and `--cap-lints=allow` when a `vendored = True`
   attribute (proposed) is set.
3. Test crate: `#[cfg(fuchsia_api_level_at_least = "HEAD")] const BRANCH: &str = "head";`
   and an `#[cfg(not(...))]` counterpart. A Bazel `rust_test` on host, or a build-time
   `static_assert`, checks the `HEAD` branch.

### Acceptance criteria
- [x] The test crate builds for both Fuchsia targets and takes the `HEAD` branch
  (checked by a build assertion, not by inspection).
- [x] The generated cfg list for a pinned `version_history.json` matches upstream's
  output for the same input (golden file from upstream's generator, or a hand-checked
  golden).
- [x] A lint that is denied by default in first-party code is allowed under
  `vendored = True`.

- Review focus: cfg semantics against upstream (off-by-one on `less_than`), and the

## What upstream does (fuchsia.git at `b5274053cc0f`)

- **Generator:** `build/bazel/versioning/rustc_api_level.bzl` (not under
  `build/bazel/rules/rust/`). For each target level in `idk_buildable_api_levels` plus
  NEXT, HEAD, PLATFORM, and for each level in `all_numbered_api_levels + [NEXT, HEAD,
  PLATFORM]`, it emits `at_least="L"` when `int(L) <= int(target)`, else
  `less_than="L"` (integers from `api_level.bzl`: NEXT 4291821568 < HEAD 4292870144 <
  PLATFORM 4293918720). It returns a `select()` keyed on
  `//build/bazel/versioning:is_api_level_<target>`; that flag defaults to `PLATFORM`.
- **Input:** `@fuchsia_build_info//:args.bzl`, which GN writes (`build/bazel/BUILD.gn`,
  levels stringified) from `build/config/fuchsia/get_platform_version.py` run on the
  source tree's `sdk/version_history.json`. `idk_buildable_api_levels` defaults to the
  `supported` levels plus NEXT.
- **Where it is applied:** at the toolchain level. Every `rust_toolchain_with_build_flags`
  in `build/bazel/toolchains/rust/rust.BUILD.bazel` (host linux-x64 and linux-arm64
  included) has `extra_rustc_flags = get_rustc_api_level_flags()`. The wrappers in
  `build/bazel/rules/rust/` add only `--cap-lints={rust_cap_lints}` (`common.bzl`; GN
  default `deny`) and a `lint_config` default.
- **GN** emits the same list for GN-built Rust (`build/rust/BUILD.gn`,
  `generated_file("api_level_cfg_flags")` from `target_api_level_range.gni`), with all
  `at_least` flags first; for these inputs that is the same order.
- **Third-party** code in GN gets `//build/config/rust:cap_lints_allow`
  (`--cap-lints=allow`).

### Decisions (details in the notebook)

1. **Toolchain level, as upstream.** The placeholder M2 left in
   `toolchain/rust.BUILD.bazel` is filled; the wrappers do not add cfgs. So every Rust
   crate built with these toolchains (including plain `rules_rust` targets such as
   `examples/hello_rust`, and later crates.io crates) gets the cfgs, as upstream.
2. **`select()` keys are rules_fuchsia's.** `@fuchsia_sdk//constraints:api_level_<L>`
   (the settings `--override_fuchsia_api_level` drives) replace upstream's
   `is_api_level_<L>`; one key for each level the flag accepts (27–32, NEXT, HEAD), no
   `//conditions:default`.
3. **Host gets PLATFORM directly (dead end first).** A single `select()` for all three
   toolchains failed host analysis: rules_fuchsia's flag rule fails ("An API level has
   not been specified…") whenever it is analyzed unset, which a `config_setting` on it
   does. Upstream's host code builds at its flag's default, PLATFORM, so the host
   toolchain takes the PLATFORM list as a plain list. Consequence: proc macros and other
   exec-config code always see PLATFORM (shown below).
4. **Input ordering.** The IDK's `version_history.json` is written with sorted keys
   (`api_levels`: `10…32, 4…9`; `special_api_levels`: `HEAD, NEXT, PLATFORM`) and adds a
   `status` field; the source tree's is `4…32` and `NEXT, HEAD, PLATFORM`. Upstream's
   `get_platform_version.py` fails its own positional assertion on the IDK copy. The
   port sorts numbered levels numerically and checks special levels by name and by
   `as_u32` against `get_integer_for_api_level`. Levels, phases and ABI revisions are
   otherwise identical to the source file at the revision.
5. **A repository rule of its own** (`toolchain/api_levels.bzl`), so the file defining
   the 3 GB IDK repository is untouched (verified: no refetch).
6. **The golden test does not follow the lock.** It runs the same repository rule on
   pinned copies (the IDK's and the source tree's file for this release), so a new
   release does not break it (M15: zero manual edits).
7. **No default build-flags toolchain** (M2 "known difference" 1, which M4 was to
   revisit): kept as is. Upstream's `@fuchsia_build_info//default_build_flags:all` is
   derived from GN configs the overlay does not have; the flags it would add are the
   ones `rust.BUILD.bazel` already writes out.
8. **`vendored = True`** replaces `--cap-lints=deny` with `--cap-lints=allow` (rustc
   rejects a second `--cap-lints`, so it is not appended).

## Deviations from the plan text

- **Cfgs are not applied by the wrappers** (plan step 2, design §4.2 "Rust rules"):
  upstream applies them in the toolchain, so the overlay does too. Design §4.2's
  sentence "adding `--cap-lints` for vendored code and the API-level cfg list from
  `rustc_api_level.bzl`" describes the wrapper; the orchestrator may want to amend it.
- **No edition default** (plan step 2): upstream's wrappers and toolchains set none, and
  every upstream `BUILD.bazel` passes `edition`; rules_rust fails a target without one.
- **Input from `@fuchsia_idk`, not `@fuchsia_sdk`** (plan step 1 allows either): the
  generated `@fuchsia_sdk` does not carry `version_history.json`.
- **Generator location:** upstream's is `build/bazel/versioning/`, not
  `build/bazel/rules/rust/` as the plan says.
- **Plan repair:** the M3 checkpoint `9c15cd9` had dropped the detailed entries for M4–M10
  and I2; they are restored verbatim from `c860458` (process-log entry filed).

## Limitations and open items

- `with_unit_tests`, `with_host_unit_tests` and `test_deps` are accepted but generate
  nothing until M16 (R9). Upstream BUILD files that set them (e.g. `zx-types`,
  `with_host_unit_tests = True`) load, but silently get no test target.
- `rustc_test` and `rustc_embed_files` are not ported (M16 / when needed).
- Exec-config code (proc macros, build tools) always builds at PLATFORM; upstream's may
  follow its flag. No crate in scope is known to depend on the difference.
- The goldens are for this release's `version_history.json`; regenerating them for a
  later release needs the recipe above (a scratch workspace and fuchsia.git at the new
  revision). M14 could script it; not needed while the fixtures stay pinned.
- M5's label rewrite must also add `vendored = True` (or decide not to) when it maps
  upstream loads to `//rules:rustc.bzl`: upstream BUILD files do not set it.

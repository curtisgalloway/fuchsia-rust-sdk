## 2026-09-28T08:04-07:00 — attempt: one runtime copy or two in the pilot's driver host
`ffx driver host list`: the pilot runs alone in its own driver host (koid 43798; no
`colocate`), in the `full-drivers` collection. `ffx target ssh "vmaps 43798"`: the only
file-backed mappings are `simple_rust_driver.so` and eight `bootfs:blob/…` VMOs.
Identified by extracting the bundle's `fuchsia.zbi` (IDK `zbi --extract`) and reading
each blob's soname: `driver_host` (`50021291…`, the executable), `libc.so`,
`libdriver_runtime.so` (`459cee0a…`, the blob M10 compared), `libasync-default.so`,
`libfdio.so`, `libtrace-engine.so`, `libstd-856d8f522a0d5cbd.so`, `libvfs_rust.so`.
None of the package's `lib/` blobs (e.g. `lib/libdriver_runtime.so` = `59bb96ec…`) is
mapped. Why: `driver_host` itself (Rust) has `DT_NEEDED` libdriver_runtime,
libasync-default, libfdio, libc, libzircon (and libstd, libvfs_rust, libtrace-engine), so
every library the pilot needs is already loaded when the driver is opened, and the
dynamic linker reuses them by soname. `ffx driver host show -r 43798` lists the pilot's
two dispatchers (`simple_rust_driver.cm-default`, `fuchsia-async`) in the host's runtime,
which is only possible with one runtime instance. `virtio-gpu-display`'s host (10685)
maps the same `459cee0a…` once. So: one copy; the packaged runtime libraries are fetched
with the package but not loaded (fallback only). The pilot's statically linked `std` sits
beside the host's `libstd` dylib (two Rust std copies, separate statics); no symptom.

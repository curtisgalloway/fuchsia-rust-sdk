QEMU (KVM when usable, TCG otherwise) and runs `hello_rust` as a component; see the
plan's [M3 entry](../implementation-plan.md).

## 2026-09-27T20:30-07:00 — decision: QEMU comes from the IDK; no new lock field
The IDK tarball is already pinned by SHA-256 (`bazel_sdk`), so QEMU inherits that pin and
the release's own choice of QEMU. A `qemu` lock field would be a second pin of the same
bytes. Alternative rejected: a CIPD `@fuchsia_qemu` repository from `manifests/prebuilts`
(duplicate download, second pin). The harness checks the IDK's `qemu.cipd_version` exists
and points ffx at `tools/x64/qemu_internal`.

## 2026-09-27T20:30-07:00 — surprise: the product bundle is not pinned by any hash
`product_bundles.json` → `core.x64` `transfer.json` (build 8669503301662913825) lists

`product_bundle.json` has no image hashes, only `product_version` and `sdk_version`

## 2026-09-27T20:34-07:00 — surprise: plain-HTTP probes through a proxy get the proxy's answer
The apt hosts "passed" that test only because I had also set `http_proxy`: the
container's agent proxy supports only CONNECT and answered the plain `HEAD http://…` with
an error status, which the probe counted as "host answered". Normally `http_proxy` is
unset here and apt (and the probe) reach the Ubuntu mirrors directly (200). Fix: for
`http://` probes a status ≥ 400 counts as blocked; for HTTPS any status counts as
reachable (HEAD gives 405 on CIPD, 400 on github.com, 404 on release-assets).
